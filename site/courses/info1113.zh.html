从源代码到有类型的值

01 / 从一个故事开始

想象工坊收到一套模型铁路图纸。检查员先拒绝不可能的连接，再制作不同工坊都能理解的标准装配说明。每个工坊仍需要自己的工具来执行说明。Java 编译器像检查员，字节码像标准说明，兼容的虚拟机提供本地执行设备。这个比喻有边界。通过检查并不能证明铁路正常运行。列车仍可能开错目的地；类型正确的程序也可能算错答案。

02 / 理解原理

常规 Java 程序写在 .java 源文件中。javac 把它编译成 .class 字节码，再由兼容 JVM 执行。编译检查可发现语法及许多类型错误。运行时检查和测试负责其他失败。变量声明的类型限制可存储的值与可执行操作。int、double、boolean 是基本类型。引用值指向对象，或为 null。int 是 32 位有符号整数；double 表示二进制浮点近似值。整数算术可能溢出。整数除法向零截断。扩大类型的转换往往自动进行；缩小类型的强制转换可能丢失信息。局部变量使用前必须确定已赋值。作用域决定名字在哪里可访问，不等于每个值在内存中的物理位置。常规 main(String[] args) 以 String 接收命令行参数。先检查数组长度，再访问下标；数字文本需要明确解析。

先认识这些词

基本类型值
直接表示数值或布尔值，而非对象引用。
强制类型转换
显式请求转换数值，可能丢失信息。
溢出
数学结果超出类型可表示的范围。

03 / 逐项读懂公式

源代码 → javac → 字节码 → JVM 执行
int 范围：−2³¹ ≤ x ≤ 2³¹ − 1
7 / 2 = 3；7 / 2.0 = 3.5

箭头表示常规编译运行流程，不要求每次 Java 启动都必须分成独立命令。x 是 int 中存储的值。两个除法例子区分了全整数操作数与包含 double 操作数的表达式。整数除法结束后再转换，无法恢复丢弃的小数。这里描述 Java 算术规则；具体处理器指令与对象布局属于实现细节，本模型不作假设。

04 / 先看一个完整例子

骑行记录程序保存 7 次行程与 2 天活动。double average = 7 / 2 得到 3.0，因为整数除法在转换前完成。写成 double average = 7 / 2.0 得到 3.5。int whole = (int) 3.9 得到 3，这是截断，不是四舍五入。把 public 类 TripStats 保存在 TripStats.java，编译后启动 TripStats。若编译器拒绝未初始化局部变量，就补齐赋值。若程序能运行却报告 3.0，说明编译成功，而数值表达式需要修改。

一步步想清楚

  1. 为什么把整数除法结果赋给 double 不能恢复小数？

    看答案

    除法已经完成，Java 之后才转换截断后的整数结果。应在相除前转换一个操作数。

  2. 为什么 50000 乘 50000 要使用 long？

    看答案

    结果 2500000000 超过 Integer.MAX_VALUE。乘法前先让至少一个操作数为 long，运算才使用更宽类型。

  3. 能解析成功是否代表所有整数都可接受？

    看答案

    不代表。解析检查表示方式；计数仍可能要求非负或不超过上限。

分开解析与有效范围

处理固定文本，不需要交互输入。

public class Main {

    public static void main(String[] args) {
        for (String text : new String[] {"12", "-2", "twelve", "2147483648"}) {
            try {
                int value = Integer.parseInt(text);
                if (value < 0)
                    System.out.println(text + ": negative count");
                else
                    System.out.println(text + ": accepted " + value);
            } catch (NumberFormatException ex) {
                System.out.println(text + ": invalid int text");
            }
        }
    }
}

java -ea Main
看输出和讲解

预期输出

-2: negative count
twelve: invalid int text
2147483648: invalid int text

按执行顺序理解

  1. 数组按固定顺序提供四种不同输入。

  2. parseInt 先检查十进制 int 表示，再执行符号规则。

  3. catch 报告转换失败，并让下一次迭代继续。

逐步读懂代码

每段文本在自己的 try 块内解析。格式合法的负整数进入领域检查。非数值文本与超过 int 范围的整数都会解析失败。

处理器位于循环内部，所以单项失败后继续处理。没有把无效值悄悄改为零。

Leon 的进一步思考

移动转换位置，而不是只换接收类型

long result = a*b 可能先在 int 运算中溢出，再赋值。写成 (long)a*b 才会扩宽运算本身。这也解释整数除法示例。

表示检查与领域检查

Integer.parseInt 能拒绝格式错误或超范围文本。另一个范围检查落实任务含义。区分两类失败有助于提供有效错误信息。

注意这个边界. 不要声称所有基本类型值都在栈上，也不要把编译成功当作正确性证明。存储取决于上下文与实现；类型正确只是正确性的一层。
检查自己的理解: (double) (9 / 4) 得到什么？怎样得到 2.25？

得到 2.0。整数除法先发生。使用 9 / 4.0 或 ((double) 9) / 4，在除法前引入浮点运算。

条件、循环与不变式

01 / 从一个故事开始

图书管理员检查推车的一层书架，再前往下一层。规则不只是不断走动。每检查完一层，所有更早的层都必须已经检查。这个始终记住的事实让进展有意义。while 像开始前先确认是否还有书架。do-while 像先检查一层再决定是否继续。增强 for 把移动路线交给遍历机制。这个比喻提醒我们：循环既需要停止规则，也需要始终成立的事实，而不只是不断变化的计数器。

02 / 理解原理

if 根据 boolean 条件选择分支。&& 与 || 采用短路求值，只有必要时才计算右侧。因此 x != null && x.isReady() 可以先保护后调用。while 在循环体前检查，do-while 在循环体后检查。for 把初始化、条件和更新写在一起。增强 for 访问元素，但不会自动提供下标。分析循环时，先写出不变式，再证明初始化建立它、循环体保持它，最后结合退出条件得到结果。还要指出一个朝终止方向变化的量。break 退出循环；continue 跳过本轮剩余内容，进入下一轮步骤。

先认识这些词

循环不变式
每次完整迭代前后都成立的事实。
短路求值
第一个布尔操作数已决定结果时，不求第二个。
进展度量
朝终止方向变化、且有界的量。

03 / 逐项读懂公式

第 i 轮开始前：total = a[0] + … + a[i−1]
0 ≤ i ≤ n；remaining = n − i
退出时 i = n：total 等于全部 n 个元素之和

a 是含 n 个数的数组。i 是下一个待处理下标。total 是已累计的和。i = 0 时空和为零。remaining 是非负进度量，每轮减一。推理假设每轮推进 i、数组长度固定且算术没有溢出。这种证明结构也适用于搜索、计数和验证循环。

04 / 先看一个完整例子

累加每日记录 [4, 0, 7]。初始化 total = 0、i = 0。不变式表示尚未处理的元素还没有被计入。第一轮后 total = 4、i = 1。第二轮后 total 仍为 4、i = 2。第三轮后 total = 11、i = 3。此时 i < a.length 为假，所以答案是 11。若改成 i <= a.length，就会访问下标 3 并失败。若数组为空，原循环不执行任何一轮，正确返回零。

一步步想清楚

  1. 为什么总和从零开始？

    看答案

    尚未处理任何值，空前缀之和为零，这建立了不变式。

  2. 什么保证循环结束？

    看答案

    i 每次增加一，不可能永远小于固定长度。剩余数量 length−i 递减到零。

  3. 为什么 text != null 要放在 text.length() 前？

    看答案

    text 为 null 时，&& 在调用 length 前停止。倒过来会先执行不安全调用。

追踪已处理前缀

每次更新后打印不变式状态。

Java 8+下载源代码 ↓

public class Main {

    public static void main(String[] args) {
        int[] values = {4, 0, 7};
        int total = 0;
        for (int i = 0; i < values.length; i++) {
            total += values[i];
            System.out.println("processed=" + (i + 1) + ", total=" + total);
        }
        int emptyTotal = 0;
        for (int value : new int[0])
            emptyTotal += value;
        System.out.println("empty total=" + emptyTotal);
    }
}

values[i]
方括号选择零起始下标 i 的元素。length 字段给出数组元素数。
total += values[i]
把当前元素加到 total 并保存新值。这里的小输入不会超过数值类型范围。

运行一个完整示例 · 02

保护空引用并在首个匹配处停止

组合短路保护与有界搜索。

Java 8+下载源代码 ↓

长代码行可左右滚动。复制或下载会保留原始代码。

public class Main {

    public static void main(String[] args) {
        String[] names = {null, "", "oak", "pine", "elm"};
        int found = -1;
        for (int i = 0; i < names.length; i++) {
            String name = names[i];
            if (name == null || name.isEmpty())
                continue;
            if (name.length() == 4) {
                found = i;
                break;
            }
        }
        System.out.println("first length-four index=" + found);
        System.out.println("matched=" + names[found]);
    }
}
在本地运行
javac -encoding UTF-8 Main.java
java -ea Main
看输出和讲解

预期输出

first length-four index=3
matched=pine

按执行顺序理解

  1. 使用 −1 作为明确的未找到标记。

  2. 先用 continue 跳过无效项，再调用其他 String 方法。

  3. 保存首个匹配索引，并用 break 退出循环。

逐步读懂代码

保护条件跳过缺失或空名称。name 为 null 时，|| 不调用 isEmpty。留下的名称可安全检查。

首个四字母名称 pine 在索引三。break 保持“首个匹配”的含义。本例已知存在匹配，一般调用者必须先检查 found 再索引。

Leon 的进一步思考

区分安全与进展

即使循环永不结束，不变式也可能成立。例如循环什么也不做，前缀和仍正确。必须同时说明保持的事实与递减的剩余工作量。

空情况属于设计的一部分

i<length 的求和循环对空数组自然返回零。do-while 至少进入一次，因此需要额外保护。按是否允许零次迭代选择控制结构。

注意这个边界. 对零起始数组使用 <= length 会多访问一格。把 null 检查写在方法调用之后，也无法发挥短路保护作用。
检查自己的理解: 为什么循环能保持不变式，却仍不结束？

不变式描述安全性，不描述进展。若 i 从不增加，不变式可能永远成立。证明终止还需要一个不断减小且有下界的进度量。

方法、调用记录与复制的引用

01 / 从一个故事开始

两名协调员各有一张写着同一社区公告板地址的卡片。任何一人都可修改公告板，两人都能看到变化。若其中一人把自己的卡片换成另一块公告板的地址，另一人的卡片不会改变。这可以解释把引用传入 Java 方法：复制的是引用值，对象可以共享。每次调用还得到独立工作桌，用来放局部变量。返回时可以概念上清空工作桌，但其他地方仍可访问的对象不会因此自动销毁。

02 / 理解原理

调用方法会建立新的调用记录，并用实参值初始化形参变量。Java 始终按值传递。基本类型实参复制基本值；对象实参复制引用值。重新给形参赋值，绝不会重新给调用者变量赋值。修改共享对象的字段或数组元素，仍可能被调用者观察到。每次调用都有自己的局部变量，递归调用也一样。static 方法属于类上下文，没有隐含 this。实例方法接收特定接收者对象。return 结束调用；若返回类型不是 void，还会提供一个值。明确输入、输出和副作用，可以让方法边界更易理解。

先认识这些词

实参
调用方法时提供的值。
形参
用实参值的副本初始化的新变量。
别名
指向同一对象的另一个引用。

03 / 逐项读懂公式

形参值 ← 实参值的副本
调用者 r ─┐
          ├→ 共享对象 O
被调用者 p ─┘
p = anotherObject 改变 p，不改变 r

r 是调用者的引用变量，p 是方法形参，O 是它们最初共同指向的对象。箭头表示引用，不是程序直接暴露的数字内存地址。赋值箭头表示把值复制进另一变量。这个模型同时适用于数组和普通对象。方法可以刻意返回新引用，但调用者必须把返回值赋给自己的变量，才能改变该变量。

04 / 先看一个完整例子

设 int[] scores = {6, 8}。方法以 x 接收 scores，先执行 x[0] = 10，再执行 x = new int[]{1, 2}。第一句把共享原数组改成 [10, 8]。第二句只让局部形参 x 指向新数组。返回后，scores 仍指向 [10, 8]。若方法返回 x，而调用者写 scores = replace(scores)，调用者就明确采用返回的 [1, 2]。区分对象修改与引用重新赋值，就能解释两种结果，无需错误地称 Java 为按引用传递。

将这个短例子另存为 ReferenceDemo.java，放在单独文件夹中。运行：

        x = new int[]{1, 2};
    }
    public static void main(String[] args) {
        int[] scores = {6, 8};
        change(scores);
        System.out.println(Arrays.toString(scores)); // [10, 8]
    }
}

一步步想清楚

  1. 哪种赋值效果可跨越方法边界？

    看答案

    写 x[0] 改变共享数组；给 x 赋新数组只改变形参变量。

  2. 调用者怎样采用新数组？

    看答案

    返回新引用，再由调用者赋给自己的变量。这样调用者明确改变自己的引用。

  3. 为什么递增 Integer 不改变调用者变量？

    看答案

    Integer 不可变。拆箱、相加与装箱只是为局部形参产生替代值。

数组、不规则网格与浅复制

01 / 从一个故事开始

储物柜抽屉从零编号。订购五个抽屉的柜子会固定大小，却不会在里面自动创建五件工具。用于存放工具的抽屉可以为空。柜中柜可以包含不同大小的内柜，也可以有内柜尚未到货的空位。复制外柜标签，不等于复制内柜全部物品。这个比喻解释了数组长度固定、引用元素默认为 null、多维数组允许不规则形状，以及复制时必须明确深度。

02 / 理解原理

数组是对象，长度固定，元素具有同一种组件类型。有效下标从零到长度减一。基本类型元素获得对应默认值；引用元素初始为 null。Java 二维数组是数组引用的数组，因此各行可以长度不同，也可以为 null。遍历每个已分配的行时，要使用该行自己的长度。把一个数组变量赋给另一个会产生别名，二者指向同一数组。clone 创建新的外层数组，但只是复制元素。元素若为引用，其对象仍共享。引用类型数组具有协变性，因此某些赋值可以通过编译，却需要运行时存储检查。泛型刻意采用不同规则，以避免这种特定风险。

先认识这些词

不规则数组
各行长度不必相同的数组。
浅复制
新外层容器仍共享其引用的内部对象。
元素类型
数组允许存入的元素类型。

03 / 逐项读懂公式

有效下标：0 ≤ i < a.length
不规则网格格数 = 对所有非 null 行求 Σ row.length
outerCopy = original.clone()：outerCopy ≠ original；行仍可能共享

i 是整数下标，a 是非 null 数组。Σ 表示把每个已分配行的长度加起来。所有行等长的矩形只是特殊情况。外层数组不相等表示身份不同，不表示内容不同。外层 clone 不会递归复制嵌套数组。复制深度取决于后续代码是否需要独立修改原来共享的元素。

04 / 先看一个完整例子

创建 int[][] rack = {{2, 5}, {9}}。共存三个数字，不是四个，因为第二行长度为一。把外层数组 clone 给 copy。执行 copy[0][1] = 7 也改变 rack[0][1]，因为两个外层数组仍指向同一第一行。再执行 copy[1] = new int[]{4, 6, 8}，只替换 copy 的第二行引用；rack 第二行仍为 [9]。要隔离全部整数格，还需复制每个非 null 行。若行内存放可变对象，还要进一步决定是否复制这些对象。

    看答案

    三个：第一行两个，第二行一个。只有已确定为矩形时才能行数乘列数。

  2. outer.clone 会隔离行内元素吗？

    看答案

    不会。它复制的是行引用。需要独立修改单元时，应逐行克隆基本类型数组。

  3. 为什么 Object[] 别名不能向 String[] 写任意值？

    看答案

    实际数组仍保留 String 元素类型，运行时存储检查会拒绝不兼容对象。

内存图：栈、堆、引用与垃圾回收

01 / 从一个故事开始

想象酒店前台。每位客人带着一张小房卡，上面写着房间号。房间本身很大，留在大楼里。如果两位客人拿着同一个房间的房卡，其中任何一位挪动家具，两个人都看得到。复制一张房卡得到的是第二张卡，不是第二个房间。房卡也可以是空白的，没有对应任何房间。而一个没有人持卡、走廊里也没有任何指示牌指向的房间，酒店可以把它清空重新使用。

内存图就是把房卡和房间画出来。房卡放在左边的方框里，因为它们是正在运行的方法的变量。房间放在右边，因为它们是对象和数组。从每张卡到它的房间画一个箭头。动手画图，是弄清“为什么一处改了、另一处没变”的最快办法。

02 / 理解原理

运行中的 Java 程序有两块和画图有关的区域。栈为每个已经开始、尚未返回的方法调用保存一个帧，帧里放着这次调用的参数和局部变量。方法被调用时压入一个帧，返回时弹出。堆保存所有用 new 创建的对象和数组，只要程序还能到达它们，它们就一直留在那里。

变量画成一个带标签的方框。基本类型变量（int、double、boolean、char 等）的值就放在方框里面。引用变量里放的是一个引用，画成指向对象的箭头，或者写 null 表示没有对象。复制变量就是复制方框里的内容。对引用来说，就是复制箭头，所以现在有两个变量指向同一个对象，这叫别名（alias）。对引用使用 == 是在问两个方框里是不是同一个箭头；对基本类型则比较值。equals 方法比较内容，但前提是这个类这样定义了它。

数组是堆上的一个对象。把它画成一排单元格，每个单元格上方标出下标，旁边写出长度。int[] 的单元格里放数字。Box[] 的单元格里放箭头，开始时都是 null。二维数组是指向数组的箭头组成的数组。String 也是对象，而且创建之后不能修改。

画法约定如下。栈画在左边，每个方法调用一个方框，最新的调用放在最下面。每个变量画一个带标签的小方块。堆画在右边，每个对象是一个方框，写出它的类和字段。每个箭头从变量方框的内部出发，终止在对象的边缘。每执行一条会产生改变的语句，就重新画一幅图，这样就能对比前后的图。静态字段可以放进一个标着 static 的单独方框。

如果从某个根出发有一串箭头能到达一个对象，这个对象就是可达的。根是仍在运行的方法的局部变量，以及静态字段。不可达的对象就是垃圾。程序再也用不到它，Java 系统可能在你无法预测的某个时刻回收它的内存。System.gc() 只是一个请求。一种简单的回收方法是标记清除。标记阶段：从每个根出发，顺着箭头走，给遇到的每个对象做标记。清除阶段：访问每个对象，释放没有标记的对象，并清除标记。因为可达性是从根开始算的，所以两个互相引用的垃圾对象也会被回收。Java 里的“内存泄漏”则是另一种问题：对象仍然可达，例如被一个静态列表保存着，但程序其实已经不需要它们。真正的回收器更复杂，有分代和并发工作，但遵循的都是可达性这个思想。

先认识这些词

栈帧
栈中保存一次方法调用的参数和局部变量的部分。
堆
存放对象和数组的区域，它们一直存在到再也无法到达为止。
引用
标识某个对象的值，画成箭头；它也可以是 null。
别名
持有同一个引用的第二个变量，这样两个变量到达同一个对象。
可达
某个根能通过一串引用到达的对象。
标记清除
一种回收方法：先标记从根可达的所有对象，再释放其余对象。

  n  [ 5 ]
  p  [ * ]------------------->  #1  Box { value = 7 }
  q  [ * ]------------------->  #1  （箭头指向同一个目标）
  x  [ * ]------------------->  int[2]  [0]=1  [1]=20
  r  [ null ]

可达(o)  ：从某个根出发有一串箭头到达 o
垃圾     = 全部对象 - 可达对象
标记     ：从每个根出发，标记到达的所有对象
清除     ：释放每个未标记的对象，然后清除标记

带星号的方框是引用变量。箭头从方框出发，终止在某个对象上。方框里的数字，如 5，是直接存放的基本类型值。“根”是可达性的起点，即仍然有效的局部变量和静态字段。“全部对象减去可达对象”是集合的差：留下的恰好是没有任何根能到达的对象。

这幅图只是一个模型。它省略了对象头、字符串池以及静态字段真正的存放位置等细节，因为这些细节不会改变关于共享和可达性的那些问题的答案。

04 / 先看一个完整例子

先看 int[] a = {4, 6}; 和 int[] b = a;。只有一个数组、两个箭头。执行 b[0] = 9; 之后，a[0] 和 b[0] 都是 9，因为数组是共享的。现在执行 b = new int[]{1};。只有 b 的箭头移到了新数组。旧数组仍然是 {9, 6}，a 依旧能到达它。接着执行 a = null;。现在没有任何变量能到达 {9, 6}，它就成了垃圾，可以被回收。数组 {1} 继续存活，因为 b 能到达它。

再看标记清除模型：共有 9 个对象和两个根。第 1 次回收标记了 6 个对象，即 A、B、D、C、E 和 F，清除了其余 3 个：G、H 和 I。e = null 之后，根只能到达 A、B、D 和 C，所以第 2 次回收清除 E 和 F，堆里还剩 4 个对象。a.right = null 之后，第 3 次回收清除 C，剩下 3 个对象。

一步步想清楚

  1. 基本类型变量的方框里放什么？引用变量的方框里放什么？

    看答案

    基本类型的方框里放值本身，例如 5。引用变量的方框里放指向对象的箭头，或者 null。

  2. 为什么方法里的 b.value = 1 会改变调用者的对象，而 b = new Box(1) 不会？

    看答案

    前者顺着箭头去修改共享的对象。后者只移动方法自己的箭头。参数是箭头的副本，不是调用者的变量本身。

  3. 互相引用的两个垃圾对象能被回收吗？

    看答案

    能。可达性从根开始计算。如果没有根能到达其中任何一个，两者都是垃圾，不管它们引用了什么。

  4. 对于值相同的两个盒子，p == r 和 p.equals(r) 有什么区别？

    看答案

    p == r 问的是两个箭头是否相同，所以对两个不同的盒子为假。p.equals(r) 只有在类重写了 equals 时才比较内容；默认情况下它也比较身份。

import java.util.ArrayList;
import java.util.List;

public class Main {
    /** One heap object with up to two outgoing references. */
    static final class Obj {
        final String name;
        Obj left;
        Obj right;
        boolean marked;

        Obj(String name) {
            this.name = name;
        }
    }

    /** A model of the heap: it knows every object, so it can sweep. */
    static final class Heap {
        final List<Obj> all = new ArrayList<Obj>();

        Obj alloc(String name) {
            Obj o = new Obj(name);
            all.add(o);
            return o;
        }

        /** Mark: follow references from a root, flagging everything reached. */
        void mark(Obj o, StringBuilder order) {
            if (o == null || o.marked) {
                return;
            }
            o.marked = true;
            order.append(o.name).append(' ');
            mark(o.left, order);
            mark(o.right, order);
        }

        /** Sweep: drop every unmarked object, then clear the marks for next time. */
        String sweep() {
            StringBuilder freed = new StringBuilder();
            List<Obj> kept = new ArrayList<Obj>();
            for (Obj o : all) {
                if (o.marked) {
                    o.marked = false;
                    kept.add(o);
                } else {
                    freed.append(o.name).append(' ');
                }
            }
            all.clear();
            all.addAll(kept);
            return freed.toString().trim();
        }

        void collect(String title, Obj... roots) {
            StringBuilder order = new StringBuilder();
            for (Obj root : roots) {
                mark(root, order);
            }
            String freed = sweep();
            System.out.println(title);
            System.out.println("  marked in order: " + order.toString().trim());
            System.out.println("  freed: " + (freed.isEmpty() ? "nothing" : freed));
            System.out.println("  heap now has " + all.size() + " objects");
        }
    }

    /** A diamond: A refers to B and C, and both refer to D. Only A is returned. */
    static Obj buildDiamond(Heap heap) {
        Obj a = heap.alloc("A");
        Obj b = heap.alloc("B");
        Obj c = heap.alloc("C");
        Obj d = heap.alloc("D");
        a.left = b;
        a.right = c;
        b.left = d;
        c.left = d;
        return a;
    }

    /** A cycle: E and F refer to each other. */
    static Obj buildCycle(Heap heap) {
        Obj e = heap.alloc("E");
        Obj f = heap.alloc("F");
        e.left = f;
        f.left = e;
        return e;
    }

    /** Its local variables vanish on return, so nothing can reach these objects. */
    static void leaveGarbage(Heap heap) {
        heap.alloc("G");
        Obj h = heap.alloc("H");
        Obj i = heap.alloc("I");
        h.left = i;
        i.left = h;
    }

    public static void main(String[] args) {
        Heap heap = new Heap();
        Obj a = buildDiamond(heap);
        Obj e = buildCycle(heap);
        leaveGarbage(heap);
        System.out.println("heap starts with " + heap.all.size() + " objects");
        System.out.println("roots are variables a and e; G and the H-I pair are unreachable");

        heap.collect("collection 1", a, e);

        e = null;
        heap.collect("collection 2 after e = null", a);

        a.right = null;
        heap.collect("collection 3 after a.right = null", a);
    }
}

逐步读懂代码

这是算法的模型，不是真正的 Java 垃圾回收器。Heap 类保存了它创建的每个对象的列表，这样清除阶段才能访问所有对象。真正的回收器则是通过扫描内存区域来找到对象。

三个辅助方法构建出这张图。buildDiamond 创建 A，它引用 B 和 C，而 B 和 C 都引用 D。buildCycle 创建 E 和 F，它们互相引用。leaveGarbage 创建单独的 G，以及互相引用的 H 和 I。辅助方法返回时，它的局部变量随栈帧一起消失，所以再没有东西能到达 G、H 或 I。唯一的根是 main 里的变量 a 和 e。

第 1 次回收从根出发，顺着引用走。标记顺序是 A、B、D、C、E、F。D 只被访问一次，虽然有两个对象引用它。所有没被标记的对象都被清除：G、H 和 I。H 和 I 虽然还互相引用，但没有任何根能到达它们，所以环并不能让它们存活。执行 e = null 之后，第 2 次回收只有根 a，于是 E 和 F 被清除，尽管它们各自还引用着对方。执行 a.right = null 之后，从 A 已经到不了 C，所以第 3 次回收清除 C；但 D 留下来，因为 B 仍能到达它。

Leon 的进一步思考

每条语句画一幅图

别名造成的错误，表现为第一幅出现两个箭头指向同一个方框的图。如果一个列表像是自己变了，就找出这幅图。它前面的那条语句，通常就是复制了引用而不是复制对象的那一行。每一步都画图只要几分钟，却能省下几小时的猜测。

有垃圾回收的语言里，泄漏就是可达性错误

一个保存每个请求对象的静态列表，会让它们全部保持可达，所以没有一个能被回收。把根画出来，就能看出静态列表是罪魁祸首。解决办法是删掉不再需要的条目，或者放弃这个静态引用，而不是调用 System.gc()。

模型可以比真实机器更简单

标记清除模型保存了每个对象的列表，真实的 Java 系统并不需要这样做。真实的回收器还会按对象的年龄分区，因为大多数对象很快就会死去。但是从模型得到的结论依然成立：只有可达的对象才能存活，环不会让垃圾存活。这也是简单的引用计数在环上会失败，而从根开始追踪不会的原因。

注意这个边界. 代码复制引用时，不要多画一个对象：Box q = p; 增加的是一个箭头，不是一个方框。把变量设为 null 并不会删除对象，它只是去掉一个箭头；只要还有别的箭头能到达这个对象，它就一直存在。也不要依赖 System.gc() 或终结器去关闭文件、释放资源，应当自己关闭。
检查自己的理解: 执行 int[] a = {4, 6}; int[] b = a; b = new int[]{1}; a = null; 之后，数组 {4, 6} 还可达吗？

不可达。起初 a 和 b 都能到达它。后来 b 被改指新数组，a 又变成 null，没有任何变量能到达 {4, 6}。它是垃圾，可以被回收。数组 {1} 通过 b 仍然可达。

文本值、相等性与构建器

01 / 从一个故事开始

在另一张说明纸上写“改成大写”，不会改动已经打印的票。请求大写票会产生另一张票。除非替换自己保存的引用，原票保持原样。两张独立打印的票可以文字完全相同，却不是同一张实体票。StringBuilder 更像白板上的草稿：不断添加会修改同一工作对象，最后再输出文本。这个比喻把内容与身份分开，也解释了文本转换为什么必须返回新值，或使用可变编辑对象。

02 / 理解原理

String 是不可变引用类型。substring、replace、toUpperCase 等操作提供结果，却不改变原 String 的值。== 比较引用身份，equals 比较 String 内容。驻留机制可能让某些相等字面量共享身份，但不能据此设计一般文本比较。StringBuilder 支持可变追加，适合在循环中拼接许多文本片段。toString 产生 String 值。Java 字符串使用 UTF-16 代码单元。length 和 charAt 按代码单元工作，因此一个显示符号可能占多个 char。特别在处理补充字符时，要根据应用对“字符”的定义选择操作。

先认识这些词

不可变
对象构造后，其逻辑值不能改变。
UTF-16 编码单元
Java 字符串索引使用的一个 16 位单元。
可变字符串构建器
创建 String 前用于组合文本的可变缓冲区。

类、构造器与受保护状态

01 / 从一个故事开始

饮水器有容量和当前水位。使用者按加水或出水按钮，不会拆开面板重写刻度。构造器像安装检查，先建立有效初态。封装有价值，是因为以后每次操作都可依赖同一规则。若公开按钮仍接受不可能的数值，单纯把刻度藏在 private 盖板下没有用。this 也可这样理解：按钮操作的是当前这台饮水器，不是同一种设计制造的所有饮水器。

02 / 理解原理

类定义字段与行为，每个实例拥有自己的实例字段。构造器初始化新实例，并可在无效对象暴露前拒绝错误参数。this 表示当前接收者，也能区分字段与同名形参。private 字段让修改必须经过受检查操作，从而帮助维持不变式。getter 和 setter 不会自动带来良好封装。允许不可能状态的 setter 会破坏设计。只有完全没有声明构造器的类，才获得编译器提供的无参数构造器。static 字段属于类并被共享，应表示真正共享的事实，而不是意外的全局状态。final 引用不能重新赋值，但仍可能指向可变对象。

先认识这些词

对象不变式
每个可用对象状态都必须满足的规则。
构造器
建立新实例初始状态的代码。
防御性复制
为防止外部别名改变受保护状态而创建的副本。

03 / 逐项读懂公式

不变式：0 ≤ level ≤ capacity
fill(q)：要求 q ≥ 0 且 q ≤ capacity − level
加水后：level′ = level + q

level 与 capacity 用相同单位描述一台饮水器。q 是请求添加量，level′ 是操作后的状态。不变式在构造完成后及每次公开操作完成后都必须成立。在不变式原本成立时，用 capacity − level 检查可避免有界整数加法溢出。这些条件属于对象契约，不应只放在调用者可能绕过的图形界面中。

04 / 先看一个完整例子

构造容量 12、水位 4 的饮水器。加 5 合法，因为 5 ≤ 12 − 4；新水位为 9。随后加 4 会被拒绝，因为只剩 3 单位空间，水位保持 9。另一台容量 8、水位 0 的饮水器始终为空。若把 level 声明为 static，两台设备就会错误耦合。构造器中 this.capacity = capacity 把形参存入实例字段。capacity = capacity 只会把形参赋给自身，字段仍停留在默认值。

一步步想清楚

  1. 为什么改变 level 前先检查？

    看答案

    验证失败时旧有效状态保持完整。先改变再检查可能暴露无效状态，或需要回滚。

  2. 为什么比较 q 与 capacity−level？

    看答案

    在 0≤level≤capacity 下，剩余容量可安全计算。先算 level+q 可能在大整数时溢出。

  3. final int[] 代表元素不可变吗？

    看答案

    不代表。它固定存储的引用；除非限制访问，数组元素仍可写。

  4. 为什么 private final 数组仍然不够？

    看答案

    private 隐藏字段名，final 禁止重新赋值。getter 返回的引用仍能修改数组。应返回副本，或设计只读操作。

import java.util.Arrays;
public class Main {
    static final class ScoreSnapshot {
        private final int[] scores;
        ScoreSnapshot(int[] source) {
            if (source == null) throw new IllegalArgumentException("missing scores");
            int[] copy = source.clone();
            for (int score : copy) {
                if (score < 0 || score > 100)
                    throw new IllegalArgumentException("score out of range");
            }
            scores = copy;
        }
        int[] values() { return scores.clone(); }
        int total() {
            int sum = 0;
            for (int score : scores) sum = Math.addExact(sum, score);
            return sum;
        }
    }
    public static void main(String[] args) {
        int[] input = {70, 80, 90};
        ScoreSnapshot report = new ScoreSnapshot(input);
        input[0] = 0;
        int[] exported = report.values();
        exported[1] = 0;
        assert report.total() == 240;
        System.out.println("snapshot: " + Arrays.toString(report.values()));
        System.out.println("total: " + report.total());
        try { new ScoreSnapshot(new int[]{101}); }
        catch (IllegalArgumentException error) { System.out.println("invalid score rejected"); }
        assert new ScoreSnapshot(new int[0]).total() == 0;
    }
}

  3. 分别修改两份外部数组，再核对报告，测试的是边界保护而非初始求和。

逐步读懂代码

n 个成绩的构造和每次 values() 都花费 O(n) 时间与 O(n) 新空间。total() 花费 O(n) 时间和 O(1) 辅助空间。这是为了稳定接口而付出的成本。int[] 的元素是基本类型，复制一层足够；若元素是可变对象，还要另行决定是否复制每个对象。

工程顺序：先写不变量，再确定谁拥有数据，最后测试所有接收或返回可变数据的边界。本例是单线程程序；如果源数组正被其他线程修改，复制不能代替同步。

输入、文件与资源生命周期

01 / 从一个故事开始

文员通过服务窗口读取一叠物品表单。按词元读取时，每次取一项；按行读取时，取到下一行边界为止。切换两种习惯，可能留下意外的空余部分。工作结束要关闭窗口，即使损坏表单中断处理也一样。Java 输入有同样两项责任：一致地解释数据流，并释放提供数据的资源。垃圾回收不是负责准时关窗的文员。

02 / 理解原理

Scanner 可从标准输入或文件读取词元，并转为基本类型。nextInt 这样的词元调用不会消费随后整行，因此后面的 nextLine 可能只读到剩余的行结束边界。要明确选择解析策略，并在适当时机先验证再转换。路径表示位置，但文件可能不存在、无法读取或格式错误。读写因而同时涉及数据逻辑与失败处理。try-with-resources 在代码块退出时关闭 AutoCloseable 资源，异常退出也如此。可移植文本文件应明确字符编码。只关闭自己拥有的资源。关闭包装 System.in 的 Scanner，也会关闭共享底层输入流。

先认识这些词

词法项
按读取器分隔规则划分的一个输入单位。
行边界
逻辑输入行的结尾，其处理方式与数字词法项不同。
资源所有权
使用后负责关闭资源的责任。

03 / 逐项读懂公式

打开 → 读取或写入 → 关闭
try (资源声明) { 使用资源; }
行文本 → 验证结构 → 解析字段 → 领域对象

第一行描述资源生命周期。try-with-resources 让关闭步骤成为语言管理的控制流，不必要求每条返回路径都记得关闭。行是原始文本单位。解析把字段转成有类型值，领域验证再判断值是否合理。这些检查彼此不同。语法有效的整数 −8，仍不能表示收到的箱子数量。

04 / 先看一个完整例子

一个小型清单文件逐行写着 "lamp,3"、"chair,5"。读取完整一行，拆成恰好两个字段，去掉数量周围空白，解析为整数，再拒绝负数，最后创建条目。重复后得到两项，总数量 8。第三行 "desk,many" 无法解析为数字，应报告行号，不能默默记为零。"shelf,-2" 可以解析，却违反领域规则。把 reader 放在 try-with-resources 中，保证两种失败都仍关闭文件句柄。

    看答案

    nextInt 消耗数字，却未消耗行终止。下一次行读取取得终止符前空的剩余内容。

  2. 为什么区分解析错误与负计数？

    看答案

    前者表示文本不是合法整数；后者是合法整数，却违反数据契约。两种情况需要不同解释。

    看答案

    这样把解析与文件系统可用性分开。同一行解析器以后可接收具有明确所有权的文件读取器。

二进制流与匹配的数据布局

01 / 从一个故事开始

仓库可以在箱子上印字符 "258"，也可以用固定数量的电子开关存储该数。二者编码同一数字，但读取者必须知道收到哪种表示。把开关模式当文字读取，不会恢复原标签。二进制文件同样需要约定布局。若第一字段为数量，第二字段为重量，读写双方都必须遵循该顺序。扩展名不会提供这个约定，程序的格式契约才会。

02 / 理解原理

文本输入输出利用编码在字符与字节之间转换。二进制输入输出则按明确布局处理字节序列。DataOutputStream 可以按规定表示写入 Java 基本类型；DataInputStream 读取匹配表示。例如 writeInt 按最高有效字节在前的顺序写四字节，readInt 期待相同四字节。双方必须同意字段顺序、宽度和表示。字段截断应当视为格式失败，不能默默替换成零。若格式需要演进，应定义版本与验证规则，不能假设全部文件都由当前程序生成。二进制流也需要资源管理与输入输出失败处理。

先认识这些词

二进制布局
存储字段约定的顺序、宽度与表示方式。
字节序
高位与低位字节写出的顺序。
截断记录
所需字段字节尚未完整到达就结束的记录。

03 / 逐项读懂公式

writeInt(258) → 00 00 01 02（十六进制字节）
258 = 1 × 256 + 2
全部字段定宽时：记录字节数 = 各字段宽度之和

01 这样的每一对数字表示一个十六进制字节。数字 0 到 F 表示零到十五。四对字节表示 DataOutput 格式中的一个 32 位 int。最高有效字节在前，表示高位字节先出现。记录大小规则仅适用于已说明的定宽布局。字符串等变长字段还需长度或分隔符约定。该字节序是 API 保证，与机器本地整数布局无关。

04 / 先看一个完整例子

传感器记录先放 int 类型 stationId，再放 double 类型 temperature。写 stationId = 258、temperature = 18.5，共用 4 + 8 = 12 字节。匹配的读取者先调用 readInt 得到 258，再调用 readDouble 得到 18.5。若先调用 readDouble，就会错误解释前八字节并破坏字段边界。若文件只有十字节，末尾 double 不完整，必须触发读取失败。先在内存中测试往返，再引入文件系统行为，并独立测试缺失和截断文件。

选择列表、集合、映射与链式结构

01 / 从一个故事开始

活动组织者需要三类记录：有顺序的流程表、不重复的胸牌编号，以及从编号查找参加者的索引。List、Set、Map 分别回答这些问题。把熟悉的容器用于全部任务，会让后续操作变麻烦。列表内部可以是按编号排列的盒子，也可以是一串相连卡片。盒子便于按位置直接访问，卡片便于沿链接行进。没有一种表示适合所有任务。找到卡片的代价，可能比找到以后改动链接的代价更大。

02 / 理解原理

List 保存有序序列并允许重复。Set 表示唯一性。Map 将键关联到值，本身不是 Collection 的子类型。ArrayList 使用可扩容底层数组。按下标访问为常数时间，尾部追加为均摊常数时间，中间插入或删除要移动元素。LinkedList 使用链式节点。按下标访问需遍历；在已知端点或迭代器位置操作，可避免移动其他元素。HashMap 和 HashSet 使用哈希及相等性。在合适条件下，常见操作期望为常数时间，但不承诺遍历顺序。若调用者只需接口契约，变量应优先声明为接口类型。泛型集合用 Integer 等包装类型；还要区分列表实际大小与底层容量。

先认识这些词

列表
可重复包含相等元素的有序序列。
集合
每种相等值最多保留一个成员的容器。
映射
每个键对应一个当前关联值的结构。

03 / 逐项读懂公式

ArrayList：get(i) O(1)；尾部追加均摊 O(1)；insert(i) O(n)
LinkedList：按下标查找 O(n)；端点更新 O(1)
Map：每个相等的键对应一个当前值；Set：每个相等类保留一个成员

n 是元素数量，i 是有效下标。大 O 描述输入增大时的增长趋势，不是实际毫秒数。均摊表示一串操作的平均成本，某次扩容仍可能复制很多元素。端点更新假设已经拿到对应端点；中间操作可能包含搜索。相等类表示按集合规则被视为相等的元素，不一定是同一对象。

04 / 先看一个完整例子

组织者将到达记录 ["Mia", "Leo", "Mia"] 放入 List，保留三次事件及顺序。用这些记录创建 HashSet，大小为 2，因为重复名字等于已有成员。Map 中 "Mia" → 2、"Leo" → 1 表示计数。把 Mia 的值改为 3，不会增加第三个键。若主要任务是反复显示第 500 个到达者，ArrayList 合适。若主要任务是反复从队列两端添加和删除，应考虑队列抽象及适合该访问方式的实现。

    看答案

    重复名称在列表中仍是独立事件，在集合中却等于已有值。容器回答不同问题。

  2. 替换映射值会增加键吗？

    看答案

    相等键已存在时不会。它只更新关联，键数不变。

import java.util.*;

public class Main {

    public static void main(String[] args) {
        Deque<String> queue = new ArrayDeque<>();
        queue.addLast("oak");
        queue.addLast("pine");
        queue.addLast("elm");
        StringJoiner fifo = new StringJoiner(", ");
        while (!queue.isEmpty())
            fifo.add(queue.removeFirst());
        Deque<String> stack = new ArrayDeque<>();
        stack.push("oak");
        stack.push("pine");
        stack.push("elm");
        StringJoiner lifo = new StringJoiner(", ");
        while (!stack.isEmpty())
            lifo.add(stack.pop());
        System.out.println("FIFO=" + fifo);
        System.out.println("LIFO=" + lifo);
        System.out.println("empty poll=" + queue.pollFirst());
    }
}

身份、值相等与哈希契约

01 / 从一个故事开始

图书馆为同一账号打印两张补办卡。它们是不同塑料片，但借阅系统应识别相同账号。查找柜先按短码分组，再在组内比较完整账号身份。若等价卡被送往不同柜子，比较就没有公平机会。这解释了 equals 与 hashCode 的联系。哈希只是引导查找的提示，不是相等证明。不同账号仍可能进入同一个柜子。

02 / 理解原理

引用相等询问两个引用是否指向同一对象。类可重写 equals(Object) 定义值相等。在相关状态不变时，该关系应满足自反、对称、传递与一致性。非 null 对象与 null 应不相等。相等对象必须有相等哈希值，不相等对象允许碰撞。因此重写 equals 通常也要用同一组逻辑字段重写 hashCode。equals(Account) 这样的重载不会替代集合使用的 equals(Object)。键存入哈希集合期间，参与相等判断的字段应保持稳定。否则查找可能进入不同于插入时的桶。不可变值对象更容易维持契约。

先认识这些词

对象身份
两个引用是否表示完全同一个对象。
值相等
类定义的规则，判断两个对象是否表示相同逻辑值。
哈希冲突
不相等值拥有相同哈希码，这是合法情况。

03 / 逐项读懂公式

a.equals(b) ⇒ a.hashCode() = b.hashCode()
哈希值相等 ⇏ 对象相等
a == b 检查身份；equals(Object) 定义值关系

a、b 是正确实现相等性的类中的非 null 对象。蕴含只有一个方向：相等约束哈希，哈希本身不能证明相等。哈希值是 int，若可能值足够多，碰撞不可避免。契约要求同一次执行中的相等实例遵循此规则，并在相关字段不变时保持一致。它不要求未来每次程序执行都产生相同哈希。

04 / 先看一个完整例子

定义 final Seat 类，以不可变的 (row, number) 作为逻辑身份。独立构造两个 B 排 7 号座位。引用不同，但正确 equals(Object) 比较两字段后返回 true。hashCode 用相同字段计算，因此把二者放进 HashSet 只保留一个逻辑座位。第三个座位 B8 仍不同，即使哈希碰撞也一样。若 equals 参数只写 Seat，通过 Object 调用可能退回 Object 的身份行为。加 @Override 可在编译时暴露错误签名。

将这个短例子另存为 EqualityDemo.java，放在单独文件夹中。运行：

import java.util.HashSet;
import java.util.Objects;
import java.util.Set;

public class EqualityDemo {
    static final class Seat {
        private final String row;
        private final int number;
        Seat(String row, int number) {
            this.row = Objects.requireNonNull(row);
            this.number = number;
        }
        @Override
        public boolean equals(Object other) {
            if (this == other) return true;
            if (!(other instanceof Seat)) return false;
            Seat seat = (Seat) other;
            return number == seat.number && row.equals(seat.row);
        }
        @Override
        public int hashCode() { return Objects.hash(row, number); }
    }
    public static void main(String[] args) {
        Set<Seat> seats = new HashSet<>();
        seats.add(new Seat("B", 7));
        seats.add(new Seat("B", 7));
        seats.add(new Seat("B", 8));
        System.out.println(seats.size()); // 2
    }
}

  1. 为何同时重写 equals 与 hashCode？

    看答案

    哈希容器先用哈希寻找候选，再用相等关系区分。相等对象必须得到一致路由。

  2. 哈希相同就表示值相等吗？

    看答案

    不表示。只有相等推出同哈希，反向不成立。第二示例保留两个冲突键。

  3. 为什么把键字段设为 final？

    看答案

    稳定的相等字段有助于在键存储期间保持查找契约。final 不会递归冻结引用的可变对象。

  4. 发生哈希冲突，就一定会丢失一条说明吗？

    看答案

    不会。不同键可以共享哈希；HashMap 还会检查相等关系，所以本例保留两条记录。

import java.util.HashMap;
import java.util.Map;
public class Main {
    static final class Cell {
        private final int row;
        private final int column;
        Cell(int row, int column) { this.row = row; this.column = column; }
        @Override public boolean equals(Object other) {
            if (this == other) return true;
            if (!(other instanceof Cell)) return false;
            Cell cell = (Cell) other;
            return row == cell.row && column == cell.column;
        }
        @Override public int hashCode() { return 31 * row + column; }
    }
    public static void main(String[] args) {
        Cell a = new Cell(2, 3);
        Cell b = new Cell(2, 3);
        Cell collision = new Cell(1, 34);
        Map<Cell, String> notes = new HashMap<>();
        notes.put(a, "charging");
        notes.put(collision, "door");
        assert a != b && a.equals(b) && b.equals(a);
        assert a.hashCode() == collision.hashCode();
        assert !a.equals(collision) && !a.equals(null);
        assert "charging".equals(notes.get(b));
        System.out.println("same object: " + (a == b));
        System.out.println("same value: " + a.equals(b));
        System.out.println("lookup: " + notes.get(b));
        System.out.println("collision keeps both: " + notes.size());
    }
}

按执行顺序理解

  2. 哈希由 equals 使用的相同字段计算，因此相同坐标的哈希一致。

  3. 故意让 (1,34) 与 (2,3) 冲突：哈希都是 65，但它们仍是不同的键。

  4. 用从未插入的 b 查询。查询成功说明是按值查找。

逐步读懂代码

哈希先缩小查找范围，equals 再判断候选对象是否就是要找的键。正确方向是 a.equals(b) 成立时，二者 hashCode 必须相同。反过来不成立，示例中的冲突已经说明这一点。

公式 h = 31r + c 中，r 是行号，c 是列号。这只是教学用哈希，不是密码学哈希。Java int 运算可能回绕，但仍应保证相等值得到相同哈希。更好的分布能减少冲突，却无法让无限多种键在有限整数范围内完全无冲突。

键存入 Map 后，不要修改参与相等比较的字段。否则查询可能按新哈希查找，而条目仍留在原来的位置。不可变键可以避免这种失败；但不可变键不会让普通 HashMap 自动变成线程安全的容器。

Leon 的进一步思考

重载不等于相等方法重写

equals(Seat) 只是增加另一方法，容器调用 equals(Object)。在目标方法上加 @Override，让编译器检查这个准确要求。

合法冲突仍可能增加耗时

只要相等实现正确，返回常数哈希合法，但许多键会成为同一区域内候选。契约正确与预期性能是两件事。

注意这个边界. 不要单凭 hashCode 推断相等。键仍在哈希集合中时，不要修改参与相等判断的字段。先移除、修改、重新插入，或直接设计不可变键。
检查自己的理解: 两个不相等对象合法地返回哈希值 42，可以吗？

可以。碰撞合法，集合必须继续用相等性区分。全部对象返回 42 也能满足契约，但性能可能很差。

继承、组合与可替换性

01 / 从一个故事开始

面包房拥有烤箱，但面包房不是一种烤箱。热风烤箱若遵守相同基本承诺，则可以是一种烤箱。混淆这些关系会导致奇怪设计：仅为复用代码使用继承，顾客就可能要求面包房“预热自己”。组合让面包房把加热委托给拥有的烤箱。继承对实例的使用方式作出更强承诺。因此应先判断行为含义，再计算能省几行代码。

02 / 理解原理

子类 extends 父类，可在期待父类的地方使用，但必须遵守父类契约。Java 类只能有一个直接父类，却可实现多个接口。继承带来可访问成员与行为；构造器不被继承。子类构造器必须安排有效的父类初始化，常用 super 传入适当参数。父类私有状态应通过其行为管理，不能绕过。组合保存协作对象引用，并委托部分工作，通常更易替换和测试。public、private、包访问与 protected 决定可见性。protected 包含包内访问，跨包子类访问还有额外限制。可替换性关乎保留承诺，不只是拥有同名字段。

先认识这些词

子类型
保持父类型行为承诺、可通过父类型使用的类型。
组合
对象持有协作者，并把工作委托给它。
可替换性
用子类型替换实现后，调用者的有效预期仍成立。

03 / 逐项读懂公式

继承：SpecializedService 是一种 Service
组合：Coordinator 拥有一个 Service
子类型责任：保留使用父类型契约的调用者预期

Service 是抽象，其公开操作具有调用者依赖的含义。SpecializedService 在保留含义时增加或更换实现。Coordinator 是独立对象，引用 Service 并可委托工作。这是概念关系，不是算术。“是一种”只能作为初步检查，还需确认父类有效操作仍有效，子类结果仍符合原承诺。

04 / 先看一个完整例子

ReportPrinter 承诺对全部非 null 文本执行 print(text)。FilePrinter 可以通过写文件实现，同时保留契约。BatchReporter 包含 ReportPrinter，对每份报告调用一次。让 BatchReporter 继承 FilePrinter 会暴露无关的打印内部实现。测试中换成把字符串存起来的 RecordingPrinter。若批次含三份报告，就检查三个有序输出。所谓子类若拒绝全部超过十字符的文本，就违反了原本不限制长度的非 null 输入承诺，除非此限制原来就在共同契约中。

一步步想清楚

  1. 为什么批量报告器持有 Sink，而不是本身作为 Sink？

    看答案

    它负责安排报告顺序，单条发送交给协作者。包含关系避免暴露无关继承操作。

  2. 子类构造器为什么调用 super？

    看答案

    子类可用前，父类部分必须建立有效状态。构造器不像普通方法那样被继承。

  3. 子类型能拒绝父类型承诺接受的输入吗？

    看答案

    那会加强前置条件，破坏可替换性，除非共同契约本来就允许拒绝。

public class Main {
    static class Counter {
        private int value;
        Counter(int start) {
            if (start < 0)
                throw new IllegalArgumentException();
            value = start;
        }
        void add(int amount) {
            if (amount < 0 || amount > Integer.MAX_VALUE - value)
                throw new IllegalArgumentException();
            value += amount;
        }
        int value() {
            return value;
        }
        String describe() {
            return "count=" + value;
        }
    }
    static final class NamedCounter extends Counter {
        private final String name;
        NamedCounter(String name, int start) {
            super(start);
            this.name = name;
        }
        @Override
        String describe() {
            return name + "=" + value();
        }
    }
    public static void main(String[] args) {
        Counter counter = new NamedCounter("samples", 2);
        counter.add(3);
        System.out.println(counter.describe());
        try {
            counter.add(-1);
        } catch (IllegalArgumentException ex) {
            System.out.println("negative rejected");
        }
        System.out.println("count=" + counter.value());
    }

Leon 的进一步思考

替换协作者以测试边界

记录型实现让测试无需真实输出设备即可检查消息。报告器仍使用相同接口，因此测试直接检查其排序责任。

代码复用不能证明所有继承都合理

只有所有合法计数操作仍有意义时，继承计数器才合理。包装器需要不同契约时，应持有计数器字段，只暴露目标操作。

注意这个边界. 不要只为方便访问代码使用继承。拥有关系、不稳定实现依赖或更严格输入限制，通常需要组合或更合适的抽象。

重载选择签名，重写选择行为

01 / 从一个故事开始

服务中心先根据表单上的请求类型选择窗口，再由实际值班人员回应。重载像根据调用运行前可见的信息选窗口。重写像由实际接收者提供回应。以后改变请求内容，不会重新进行早先的窗口选择。把两步分开，就能解释常见困惑：变量里放着特殊对象，仍可能选中参数更一般的重载。

02 / 理解原理

重载方法名称相同，参数列表不同。选择依据编译时类型与适用性规则。只有返回类型不同，不能形成有效重载。构造器也可重载，并通过 this 委托另一构造器。重写为继承的实例方法提供子类型实现，签名与返回类型必须兼容。选定实例方法签名后，动态分派根据接收者运行时类选择实现。重写不能降低访问权限，也不能扩大受检查异常范围。用 @Override 捕捉错误。static 方法被隐藏，不是动态重写；字段也不动态分派。实参运行时类不会独立触发一次新的重载搜索。

先认识这些词

重载
方法同名，但参数列表不同。
重写
子类型为继承的实例方法提供实现。
接收者
实例方法被调用时作用的对象。

03 / 逐项读懂公式

1. 编译时：选择适用的方法签名
2. 运行时：对被重写的实例方法，选择接收者实现
同名 + 不同参数 → 重载
兼容的继承实例签名 → 重写

在入门例子中，签名由方法名和参数类型确定。仅返回类型不足以区分重载。接收者是实例调用中点号前的对象。编译时类型是编译器已知的变量或表达式类型；运行时类属于实际对象。这两阶段适用于普通虚实例方法。构造器、静态方法、私有方法与显式 super 调用有各自规则，不能随意说成同一种分派。

04 / 先看一个完整例子

Printer 定义 show(Object) 返回 "general"，show(String) 返回 "text"。FancyPrinter 将 show(Object) 重写为返回 "fancy general"，但继承 show(String)。令 Printer p = new FancyPrinter()，Object item = "hello"。p.show(item) 在编译时选择 show(Object)，随后执行 FancyPrinter 重写，返回 "fancy general"。p.show("hello") 则选择 show(String)，返回 "text"。两次实际值都是 String，但 item 的声明类型 Object 控制重载选择。这样可把签名选择与运行时接收者分派分别观察。

抽象类、接口与默认行为

01 / 从一个故事开始

城市可以公布自行车租借契约，却不拥有特定自行车。彼此无关的组织都能承诺相同预约与归还操作。另一边，同一制造者可以让多个车型共用车架设计，复用部分结构并留下未完成细节。公共契约像接口，部分完成的系列设计像抽象类。两者都让调用者面向一般概念，却解决不同问题。共享契约说明可依赖什么；共享实现还可管理履行承诺所需状态。

02 / 理解原理

抽象类不能直接实例化，但可声明字段、构造器、具体方法和抽象方法。具体子类必须实现所有剩余抽象方法。接口描述一种能力，可由无关类实现。在 Java 8 中，接口可含抽象方法、default 实例方法、static 方法与常量。私有接口辅助方法从 Java 9 才加入，不属于本课程 Java 8 示例。接口字段隐含为 public static final，不提供每实例可变状态。类可实现多个接口，同时只继承一个类。default 方法提供继承行为，但无关接口的默认方法冲突必须明确解决。调用者只需某项能力时，优先小接口；真正的类族需要共享实现或受控构造时，可用抽象类。

先认识这些词

抽象方法
声明了操作，但实现需由具体子类型提供。
接口
不同类都可实现的命名能力契约。
默认方法
由接口提供、可继承的实例方法实现。

03 / 逐项读懂公式

抽象类：共享状态 + 部分实现 + 必须补齐的操作
接口：共同能力契约 + 可选默认行为
具体实现必须满足全部继承的抽象义务

加号连接设计职责，不表示数字相加。共享状态是抽象父类管理的实例字段。能力是调用者无需知道具体实现就能请求的操作。必须补齐的操作是尚无主体的抽象方法。default 方法是接口中的实例实现，区别于有时也被口头称作“默认访问”的包访问。分别命名可以避免同词不同义造成混淆。

04 / 先看一个完整例子

定义 AlertSink 接口，含 void send(String text)。ConsoleSink 打印消息，RecordingSink 保存消息供测试。提醒服务接收 AlertSink，无需了解两种实现。若多个网络接收器共用连接配置和重连逻辑，抽象 NetworkSink 可管理状态，并让 send 保持抽象。具体 EmailSink 补齐行为。若两个接口提供相同签名但互不相关的 default 描述，兼实现它们的类必须明确选择或替换。不能依靠接口书写顺序决定胜者。

泛型类、类型上界与类型安全

01 / 从一个故事开始

可复用运输箱的标签注明接受哪类物品。同一种设计可以装书或乐器，却阻止书箱意外收到自行车。去掉标签写“任何东西”看似灵活，收货人却必须猜取出的类型。泛型类保留放入与取出之间的关系。上界还能增加有用承诺：例如每件物品都必须可称重，让箱子程序不猜具体种类也能调用称重操作。

02 / 理解原理

泛型用类型参数化类、接口和方法，让编译器检查输入输出关系。在 Box<T> 中，T 字段与返回 T 的 get 保留选定类型。类型实参必须是引用类型，所以使用 Integer，不是 int。T extends Number 这样的上界让泛型代码可使用 Number 操作。上界为接口时也写 extends。静态泛型方法在返回类型前声明自己的类型参数，因为它不能依赖某个实例的 T。大多数泛型信息在运行时被擦除。原始类型与未经检查的强制转换会削弱保证。new T[n] 不是通用合法的泛型数组创建方式。

先认识这些词

类型参数
由泛型类或方法声明的类型占位符。
类型界限
限制哪些类型能替换类型参数的要求。
类型擦除
编译移除许多泛型类型信息，同时保留所需检查与转换。

03 / 逐项读懂公式

Box<T>：put(T value) → get(): T
<T extends Number> double read(T value)
static <T> T first(List<T> values)

T 是类或方法某次使用时选定的引用类型占位符。第一行表示容器保留类型关系，不表示 put 立即调用 get。上界限制可选 T，也告诉编译器有哪些操作可用。静态方法声明独立 T，作用域在该方法内。first 还需要非空列表前置条件；类型安全签名不能保证元素一定存在。

04 / 先看一个完整例子

Box<String> 存入 "north"，无需强制转换便返回 String。尝试存入整数 4 是编译错误。Box<Integer> 复用相同实现，但返回 Integer。再写 static <T> T first(List<T> values)，拒绝空列表后返回 values.get(0)。输入 ["red", "blue"] 时，类型推断得到值为 "red" 的 String。输入 [8, 13] 时，得到值为 8 的 Integer。算法不变，因为它依赖位置与类型保留，不依赖 String 或 Integer 特有行为。

    看答案

    类型参数在编译期连接存储与返回类型，编译器为每次使用检查该关系。

  2. 静态方法返回类型前为何声明类型参数？

    看答案

    方法要声明自己的类型参数，不能把某实例特有的 T 当作共享静态方法的类型。

  3. 类型安全保证列表有首项吗？

    看答案

    不保证。元素类型与集合大小是不同条件，方法仍需检查空列表。

通配符与数据流方向

01 / 从一个故事开始

仓库可以把苹果箱看成某种水果箱并检查内容，却不能安全加入梨，因为实际箱子可能只允许苹果。反过来，保证能接受苹果的箱子可以再放苹果，但读取时不能保证每项都是苹果，因为它可能是一般水果箱。通配符表达这两类不完整知识。它不是装饰性的“不确定”，而是说明：当前方法不知道完整元素类型时，哪些操作仍安全。

02 / 理解原理

Java 泛型是不变的：List<Integer> 不是 List<Number> 子类型。否则接受 List<Number> 的代码可把 Double 插进承诺只放 Integer 的列表。List<? extends Number> 接受某个未知 Number 子类型的列表，因此能安全读为 Number，却不能安全加入指定的非 null Number。List<? super Integer> 接受未知元素类型为 Integer 或其父类型的列表，因此可安全加入 Integer；没有进一步证据时，读取只能得到 Object。PECS 表示生产者用 extends、消费者用 super。这是相对于方法的数据流。通配符视图不一定不可变，底层列表仍可能支持删除和清空。

先认识这些词

不变性
虽然元素类型有继承关系，List<Integer> 仍不是 List<Number> 子类型。
生产者
当前方法从中读取值的参数。
消费者
当前方法向其中写入值的参数。

03 / 逐项读懂公式

生产者：List<? extends T> → 安全读取 T
消费者：List<? super T> ← 安全写入 T
复制：来源 extends T；目的地 super T

T 是被传递值的类型。生产者向方法提供值，消费者接收方法传出的值。? 代表某一个确定但未知的类型，不是每次操作都能重新任选类型。箭头描述允许的数据流。读写安全指静态类型安全；具体集合仍可能用 UnsupportedOperationException 拒绝修改。null 是特殊写入情况，但不是忽略一般规则的理由。

04 / 先看一个完整例子

source 是含 [3, 7] 的 List<Integer>；destination 是初始含 [2.5] 的 List<Number>。复制方法可声明 <T> void copy(List<? extends T> src, List<? super T> dst)。把来源元素读为 T，再加入目的地，得到 [2.5, 3, 7]。source 的 List<? extends Number> 视图不能加入 2.5，因为隐藏类型可能是 Integer。destination 的 List<? super Integer> 视图可以加入 9，但首项只能读为 Object，因为它可能是原有 Double 2.5。

迭代器、别名与可达性

01 / 从一个故事开始

两位参观者各拿一张美术馆路线卡。每张卡记录个人当前位置；若共享同一张卡，一个人的前进就会意外改变另一个人的进度。展馆像可迭代结构，路线卡像迭代器。再想象旧展室所有公共入口都被移除。里面物品仍可能互相指向，但从仍在使用的建筑已经无法到达。第二个比喻解释垃圾回收：即使对象互相引用，只要循环整体不可达，也可能被回收。

02 / 理解原理

Iterable<T> 提供迭代器，Iterator<T> 通过 hasNext 和 next 表达遍历状态。增强 for 对 Iterable 对象使用该协议，数组另有语言支持。独立迭代器应保存独立游标。耗尽后 next 必须抛 NoSuchElementException，不能返回编造值。遍历期间的结构修改取决于集合契约。常见快速失败迭代器可抛 ConcurrentModificationException，但这不是同步策略。引用也决定对象可达性。垃圾回收可回收从活动根不再可达的对象，包括不可达循环。只把一个变量设为 null 不够，其他路径可能仍存在。回收时机不确定，也不能代替外部资源的明确清理。

先认识这些词

迭代器
保存一次遍历游标与操作的对象。
可达性
是否仍有活跃引用链到达对象。
根
可达性搜索开始处的执行引用或静态引用。

03 / 逐项读懂公式

Iterable<T>.iterator() → 独立遍历状态
hasNext() 报告是否还有元素；next() 返回元素并推进
可回收候选：活动根到对象之间没有强引用路径

T 是元素类型。独立遍历状态指需要独立遍历时使用独立游标，不表示复制整个集合。活动根包括活动执行上下文与静态引用；强路径由普通可达链接组成。最后一行只概念性描述资格，不是立即删除指令。不可达循环中的对象即使被内部引用，也可能没有活动根路径。看似不再使用、却仍被静态集合保存的对象，仍可能可达。

04 / 先看一个完整例子

列表为 ["oak", "pine", "elm"]。迭代器 a 读取 "oak"，下一步面向 "pine"。独立创建的 b 第一次 next 仍返回 "oak"。把 a 推进到结束，不应改变 b 的游标。若两个迭代器与列表都不可达，且没有其他引用，列表及其私有节点便可能可回收。若静态缓存仍保存列表，它就仍可达。通过受支持的迭代器操作删除元素，与遍历期间任意修改同一列表，是不同情况。

一步步想清楚

  1. 两个迭代器为何第一次都返回 oak？

    看答案

    每个迭代器有自己的游标。共享列表不等于共享遍历位置。

  2. 遍历中为什么使用 iterator.remove？

    看答案

    它是迭代器支持的删除最后返回元素方式。随意通过列表改结构可能使遍历假设失效。

  3. 把一个变量设为 null 能证明垃圾回收发生吗？

    看答案

    不能。其他强引用路径可能仍在。即使没有路径，也只表示有资格回收，不承诺立即回收。

把异常作为明确的失败路径

01 / 从一个故事开始

配送流程有普通路线，也有清楚标出的故障路线。地址无法辨认时，需要有能力纠正的人作决定。假装包裹已经送达，会破坏记录。分拣设备损坏又不同于缺少门牌号。异常让方法报告正常承诺无法完成，并把控制交给合适处理者。比喻也提醒我们：无论走哪条路线，装货门仍要关好，临时设备仍要释放。

02 / 理解原理

抛出异常会离开当前正常路径，向外寻找匹配 catch，必要时展开调用栈。受检查异常必须被捕获，或用 throws 声明。RuntimeException 与 Error 的子类不受检查。这是编译规则，不是严重程度的完美排序。应选择能解释契约违反或失败原因的异常，在能够恢复或转换含义的边界捕获。throws 声明并没有处理失败。较具体 catch 要写在较宽泛 catch 前。finally 在普通及异常退出时执行；受管理资源优先使用 try-with-resources。异常不全是调用者违反前置条件：输入合法，输入输出操作也可能失败。

自定义异常：受检查还是非受检查

01 / 从一个故事开始

一家咖啡馆有个规矩。厨师做不出一份订单时，不会只在店里喊一声“出问题了！”。厨师会递给服务员一张条子，上面写清楚到底出了什么问题：“牛奶用完了”，附上桌号，也许还有缺几杯。服务员就能做点合理的事，比如推荐燕麦奶。如果问题是燃气断供，没人指望服务员去修，那就直接报告给经理。

自定义异常就是这样一张条子：有明确的标题，还带着处理者需要的细节。选择受检查还是非受检查，就是选择哪一种条子。受检查异常是一份文书，路上的每个服务员要么处理，要么转交，而且编译器会检查他们确实这样做了。非受检查异常是一次紧急情况，它跳过文书，直接送到能处理它的人那里。

02 / 理解原理

标准异常的名字比较笼统。自定义异常则用你程序自己的语言命名失败，例如 InsufficientFundsException。它可以携带处理者需要的数据，也让调用者能只捕获这一种失败，而不会误捕其他的。

写一个自定义异常：受检查异常继承 Exception，非受检查异常继承 RuntimeException。不要直接继承 Error 或 Throwable。名字以 Exception 结尾。给它两个构造方法，把参数传给 super：一个只有 String 消息，另一个有消息和 Throwable 原因。为处理者需要的数据添加 private final 字段和 getter。Throwable 是可序列化的，所以要加上 serialVersionUID，否则编译器会警告。异常类不能是泛型的。

异常可以组成层次。OrderException 这样的基类代表一个家族，UnknownItemException 这样的子类代表具体的失败。调用者可以捕获基类，也可以捕获子类。要先捕获更具体的类型，因为把父类的 catch 放在子类前面，会让子类的子句永远到不了，这是编译错误。

底层失败时，把它的异常转换成你自己的异常，并把原异常作为原因传进去：throw new OrderException(message, cause)。这样 getCause() 还能给出根本原因，而你的调用者也不用依赖底层的细节。不要丢掉原因。

怎样在受检查和非受检查之间选择？问自己：合理的调用者除了停止之外，能不能做点有用的事？如果能，就设为受检查。例如文件不存在、付款金额不足、用户输入了不存在的代码。如果失败意味着有缺陷或者前置条件被破坏，例如空参数、下标越界，或者别的代码传来了 -1 的数量，就设为非受检查。受检查异常是有代价的：它们出现在方法签名里，每个调用者都必须捕获或声明，而且在 lambda 里用起来很别扭。如果把一切都设为受检查，人们就会为了让编译器闭嘴而写空的 catch 块。非受检查异常容易被忽视，所以要用 @throws 写进文档。不要用异常控制普通流程，想捕获具体类型时不要捕获 Exception，也不要悄悄吞掉异常。

先认识这些词

你自己编写的异常类，用来按你程序的语言命名一种失败。
受检查异常
编译器强制调用者捕获或用 throws 声明的异常。
非受检查异常
不需要 catch 或 throws 的 RuntimeException 或 Error。

04 / 先看一个完整例子

钱包里有 250 美分。pay(200) 成功，剩下 50。pay(100) 差 100 - 50 = 50，所以抛出差额为 50 的 InsufficientFundsException，余额保持 50。处理者补 50，变成 100，现在 pay(100) 成功，剩下 0。调用 pay(-5) 是调用者的缺陷，所以抛出非受检查的 IllegalArgumentException。

再看订单系统。"tea:2" 的价格是 300 x 2 = 600 美分。"juice:1" 没有价格，抛出 UnknownItemException。"cake:x3" 含有字符 x。辅助方法报告了它，上一层把它包装成 OrderException，并保留原异常作为原因。"cake:0" 违反了数量至少为 1 的规则，所以抛出非受检查的 InvalidQuantityException。

一步步想清楚

  1. 自定义异常的构造方法为什么要调用 super(message)？

    看答案

    消息保存在 Throwable 里。把它传上去，getMessage() 才能返回它。

  2. 为什么子类的 catch 必须在父类的 catch 之前？

    看答案

    Java 选第一个匹配的子句。父类子句放在前面，会匹配子类能匹配的一切，子类子句永远不会运行，编译器会拒绝。

  3. 如果在 catch 块里抛出新异常却不传入原因，会丢失什么？

    看答案

    会丢失根本原因和它的堆栈跟踪。之后的读者只能看到你的概括，无法知道是哪个底层失败引起了问题。

  4. 异常类什么时候应该有额外的字段？

    看答案

    当处理者需要数据才能恢复时，比如钱包例子里的差额。如果处理者不得不从消息字符串里读数字，就说明缺少一个字段。

public class Main {
    /** Checked: the caller can often fix this, so the compiler makes callers face it. */
    static final class InsufficientFundsException extends Exception {
        private static final long serialVersionUID = 1L;
        private final int shortfall;

        InsufficientFundsException(String message, int shortfall) {
            super(message);
            this.shortfall = shortfall;
        }

        int getShortfall() {
            return shortfall;
        }
    }

    static final class Wallet {
        private int cents;

        Wallet(int cents) {
            this.cents = cents;
        }

        int balance() {
            return cents;
        }

        void topUp(int amount) {
            cents += amount;
        }

        void pay(int price) throws InsufficientFundsException {
            if (price <= 0) {
                throw new IllegalArgumentException("price must be positive: " + price);
            }
            if (price > cents) {
                int missing = price - cents;
                throw new InsufficientFundsException("need " + missing + " more cents", missing);
            }
            cents -= price;
        }
    }

    public static void main(String[] args) {
        Wallet wallet = new Wallet(250);
        try {
            wallet.pay(200);
            System.out.println("paid 200, balance " + wallet.balance());
            wallet.pay(100);
            System.out.println("this line is skipped");
        } catch (InsufficientFundsException ex) {
            System.out.println("caught: " + ex.getMessage());
            System.out.println("balance unchanged: " + wallet.balance());
            wallet.topUp(ex.getShortfall());
            System.out.println("topped up " + ex.getShortfall() + ", balance " + wallet.balance());
            try {
                wallet.pay(100);
                System.out.println("second try paid 100, balance " + wallet.balance());
            } catch (InsufficientFundsException again) {
                System.out.println("still short: " + again.getShortfall());
            }
        }

        try {
            wallet.pay(-5);
        } catch (InsufficientFundsException ex) {
            System.out.println("not reached: a negative price is not a funds problem");
        } catch (IllegalArgumentException ex) {
            System.out.println("programming error: " + ex.getMessage());
        }
    }
}

            super(message);
        }

        OrderException(String message, Throwable cause) {
            super(message, cause);
        }

            char c = text.charAt(i);
            if (c < '0' || c > '9') {
                throw new IllegalArgumentException("'" + c + "' is not a digit");
            }
            value = value * 10 + (c - '0');
        }
        return value;
    }

    static int priceOf(String code) throws UnknownItemException {
        if (code.equals("tea")) {
            return 300;
        }
        if (code.equals("cake")) {
            return 450;
        }
        throw new UnknownItemException(code);
    }

    /** Translate a low-level failure into this layer's own exception and keep the cause. */
    static int total(String line) throws OrderException {
        String[] parts = line.split(":");
        int price = priceOf(parts[0]);
        int quantity;
        try {
            quantity = readNumber(parts[1]);
        } catch (IllegalArgumentException cause) {
            throw new OrderException("bad quantity in \"" + line + "\"", cause);
        }
        if (quantity < 1) {
            throw new InvalidQuantityException(quantity);
        }
        return price * quantity;
    }

    public static void main(String[] args) {
        String[] lines = {"tea:2", "juice:1", "cake:x3", "cake:0"};
        for (String line : lines) {
            try {
                System.out.println(line + " -> " + total(line) + " cents");
            } catch (UnknownItemException ex) {
                System.out.println(line + " -> unknown code " + ex.getCode());
            } catch (OrderException ex) {
                System.out.println(line + " -> " + ex.getMessage() + ", cause: " + ex.getCause().getMessage());
            } catch (InvalidQuantityException ex) {
                System.out.println(line + " -> contract violated: " + ex.getMessage());
            } finally {
                System.out.println("  processed " + line);
            }
        }
    }
}

逐步读懂代码

OrderException 是一个小家族的基类，而且是受检查的。UnknownItemException 继承它，所以调用者既可以只捕获具体的那一种，也可以捕获整个家族。InvalidQuantityException 继承 RuntimeException，是非受检查的。

Leon 的进一步思考

异常是方法契约的一部分

受检查异常出现在方法签名里，所以以后再添加一个，会破坏所有调用者。非受检查异常不出现在签名里，所以必须用 @throws 写进 Javadoc。要尽早决定哪些失败属于契约。许多现代库对大多数失败选用非受检查异常，只在真正需要做决定的情形下才保留受检查异常。

在层与层的边界转换异常，并保留原因

存储层可能因为底层错误而失败，订单层把它转换成 OrderException。这样订单层的调用者不需要了解存储的细节，而程序顶层的日志仍能打印整条原因链。这就是两种构造方法（带原因和不带原因）都值得写的原因。

字段让处理者更聪明，但消息要保持安全

shortfall 字段让处理者无需解析文本就能修复问题。这类字段应保持不可变。不要把密码、完整卡号之类的秘密放进消息，因为消息最终会出现在日志里。

注意这个边界. 不要把所有自定义异常都做成受检查的，再用 catch (Exception e) {} 去堵编译器。也不要把本来可以恢复的失败做成非受检查的，让没人去预先考虑它。包装异常时，一定要把原异常作为原因传进去。没有原因的新异常，会丢掉真正出了什么问题的证据。
检查自己的理解: 一个方法解析用户键入的数量。另一个方法从本该检查过的代码那里收到了 -1 的数量。哪一个用受检查异常，哪一个用非受检查异常？

解析用户文本用受检查异常，因为程序可以让用户重新输入。从别的代码收到 -1 是调用者的缺陷，所以用非受检查的 IllegalArgumentException。

枚举与有限状态模型

01 / 从一个故事开始

包裹可以等待、运输中或已送达。用便签随意写状态，容易拼错或创造“差不多算送到”等标签。预先印好的正式标记可以收窄词汇。但词汇正确不保证流程合理：从已送达直接回到等待，仍可能违反流程。enum 提供有限标签集合，转移规则控制标签之间如何移动。同时看清两者，才能避免把类型安全状态名误当完整正确的状态机。

02 / 理解原理

enum 定义该枚举类型中固定的一组命名实例。它在编译时阻止混用无关标签，也可包含字段、方法和构造器。每个常量甚至可提供专门行为。枚举实例可用 == 比较，因为每个声明常量对应唯一实例。优先使用有意义的方法或明确转移表，避免分散的字符串比较。状态机结合当前状态、事件和转移规则，决定下一状态或拒绝事件。枚举让状态空间明确，却不会自动约束所有转移。不要把 ordinal 持久保存为长期标识，因为常量重排会改变编号。名称或明确稳定代码通常更清楚。

先认识这些词

枚举常量
枚举定义的固定集合中的一个命名实例。
状态转换
把当前状态和事件变为下一状态或拒绝的规则。
稳定编码
不依赖声明位置的明确外部标识。

03 / 逐项读懂公式

δ(state, event) = 下一状态或拒绝
δ(QUEUED, dispatch) = IN_TRANSIT
δ(IN_TRANSIT, confirm) = DELIVERED
δ(DELIVERED, dispatch) = 拒绝

δ 是转移函数。state 属于枚举定义的有限集合，event 是应用接收的动作。拒绝表示该状态事件对在本模型中没有允许转移。模型必须说明如何报告拒绝，以及是否保留状态。这些规则描述所选包裹流程，不是普遍领域规则。枚举常量只是状态值，不是保存包裹身份等数据的完整对象。

04 / 先看一个完整例子

包裹 P7 从 QUEUED 开始。dispatch 使其进入 IN_TRANSIT。第二次 dispatch 被拒绝，因为已离开队列，状态保持 IN_TRANSIT。confirm 再使其进入 DELIVERED。后来的 dispatch 再次被拒绝。测试要检查三个允许状态，以及契约中重要的所有不支持状态事件组合。若加入 RETURNED，应重新检查转移模型与测试。仅增加枚举常量，不会自动告诉现有操作退回包裹应如何行动。

一步步想清楚

  1. 枚举能阻止所有无效转换吗？

    看答案

    不能。它只限制状态名称。必须由独立操作拒绝不支持的状态事件组合。

  2. 枚举值为何可用 == 比较？

    看答案

    每个声明常量都是固定实例，身份就代表这个枚举值。

  3. 为什么避免持久保存 ordinal？

    看答案

    ordinal 是声明位置。插入或重排常量会改变它，显式编码则可保持格式契约。

        }

断言、测试与有用边界

01 / 从一个故事开始

电梯检查员不会只在安静时从二楼坐到三楼。他们检查底层、顶层、空载、容量上限和非法请求，因为边界会暴露普通行程隐藏的错误。软件测试同理。维修面板中的警示灯像语言断言：适合检测内部假设，却不适合作为阻止乘客选择不可能目的地的唯一保护。无论诊断断言是否开启，公开输入验证都必须在正常运行时有效。

02 / 理解原理

测试把观察行为与期望结果比较。根据契约选择正常情况、边界、非法输入及相关状态转移。黑盒测试关注公开行为；白盒推理可找出未测试分支，但不应让测试依赖每个实现细节。Java assert 可以被关闭，适合内部一致性检查，却不能作为公开输入唯一验证。JUnit 等测试框架的断言在测试中执行，不依赖 Java assert 开关。每个测试都应清晰且确定，既检查正常返回，也检查异常行为。通过测试会提升已覆盖情况的信心，却不能证明没有其他缺陷。

先认识这些词

测试初始环境
单个测试案例准备的对象与输入。
边界案例
位于规则接受边界上或附近的输入。
回归测试
保留用于发现已理解缺陷再次出现的测试。

03 / 逐项读懂公式

准备 Arrange → 执行 Act → 验证 Assert
合法整数范围 1…m 的边界集合：{0, 1, m, m+1}
期望结果包含值、状态变化与异常行为

Arrange 建立初态，Act 调用待测行为，Assert 将观察与契约比较。m 是简单连续整数范围的最大合法输入。边界集合采样两侧边界及紧邻非法值；若逻辑还有分支，仍需其他值。期望行为可包含拒绝后的状态不变。覆盖率统计执行到哪里，不衡量期望判断的质量。

04 / 先看一个完整例子

预约对象有 8 个位置，当前占用 3 个。测试 reserve(2)，期望变为 5。在独立初态中测试 reserve(5)，期望为 8。测试 reserve(6)，应拒绝并保持 3。也测试负请求，并依据契约决定零是否合法。这覆盖一般成功、恰好满额、超容量与非法符号。若随意复用已修改对象，第二个测试会依赖第一个，因此每个案例都应建立自己的初态。

    看答案

  2. 公共输入验证为何不能只靠 Java assert？

    看答案

    assert 可以关闭。普通条件与异常才能始终落实输入契约。

    看答案

    不能。它记录的是执行。测试仍需把有意义观察与独立推导的预期比较。

            throw new IllegalArgumentException("empty input");

        for (int value : values)
            sum += value;
        return (double)sum / values.length;

        double actual = average(values);
        if (actual != 4.5)

        try {
            average(new int[0]);
        } catch (IllegalArgumentException ex) {
            rejected = true;
        }
        if (!rejected)
            throw new AssertionError("empty input must fail");
        System.out.println("fractional average=" + actual);
        System.out.println("empty input rejected=" + rejected);
    }
}

递归、调用树与结果复用

01 / 从一个故事开始

嵌套文件夹可以这样计数：询问各子文件夹大小，再加上自身的一。每次请求处理更小部分，空文件夹停止下探。若多个路径又请求同一昂贵计算，文员可以第一次记下答案，以后复用。但记录必须对应相同输入与假设。这两幅图区分递归与记忆化。递归把问题拆成更小调用；记忆化避免重复等价工作。

02 / 理解原理

递归方法需要基本情况，以及不断接近基本情况的递归调用。每个活动调用都有自己的局部变量，并增加调用栈深度。正确性可这样论证：假设较小实例正确，再说明它们的结果如何组成当前答案。递归遍历对象结构，还需处理循环与重复引用的规则；任意对象图不自动是一棵树。记忆化按决定结果的输入缓存答案。重复子问题多时有用，但消耗内存；相关状态改变而未失效缓存，会产生错误。即使数学算法终止，深递归仍可能使 Java 栈溢出。深度可能很大时，应考虑迭代替代。

先认识这些词

基本情况
无需继续递归即可回答的情况。
记忆化
按决定结果的输入缓存计算结果。
调用深度
同时活动的嵌套调用数量。

03 / 逐项读懂公式

ways(0) = 1；ways(1) = 1
ways(n) = ways(n−1) + ways(n−2)，n ≥ 2
此递推的缓存状态数 n+1；时间 O(n)，存储 O(n)

ways(n) 统计用一步或两步恰好走完 n 阶的移动序列，n 为非负整数。零阶有一种空序列。时间界假设每个缓存状态只算一次，且算术成本为常数；只有结果仍放得进所选定宽类型时，该算术假设才适用。递归记忆化最坏还需要 O(n) 调用栈。大规模精确答案需要更宽或任意精度类型，会改变算术成本模型。

04 / 先看一个完整例子

四阶楼梯中，ways(2) = 1 + 1 = 2，ways(3) = 2 + 1 = 3，ways(4) = 3 + 2 = 5。五种模式为 1111、112、121、211、22。直接递归会在多个分支重算 ways(2)。使用缓存时，ways(0) 到 ways(4) 各算一次并复用。负 n 应被拒绝，或明确设计另一契约。n 大到让 int 溢出时，即使递归逻辑正确，数值答案仍会错误，除非改变表示。

    看答案

    覆盖零阶有一种空移动序列。这个基本情况让递推正确统计组合。

  2. 记忆化消除了什么？

    看答案

    消除同一状态的重复计算，不一定缩短最长依赖链，也不一定避免深栈失败。

  3. 缓存键为什么必须包含允许步长规则？

    看答案

    允许移动规则改变后，同一 n 的答案可能改变。只按 n 缓存仅在规则固定时有效。

匿名类、lambda 与捕获上下文

01 / 从一个故事开始

咖啡馆需要一条小规则，决定哪些订单收到提醒。每条规则都请一位有名字的专家未必必要，传入一张短说明往往更清楚。但说明仍需已知格式：接收什么输入，返回什么答案。lambda 填充这样的单操作契约。匿名类更像临时员工，有自己的身份，也可能有额外内部状态。二者都避免独立命名类，却不会产生完全相同的作用域与身份行为。

02 / 理解原理

匿名类表达式创建一个在当前位置声明的类的实例，扩展一个类或实现一个接口。lambda 为函数式接口提供实现；完整判断需考虑继承及 Object 方法规则，其抽象方法契约只对应一个函数操作。default 和 static 方法本身不增加抽象义务。参数及返回类型必须匹配目标接口。lambda 只能捕获 final 或事实上的 final 局部变量。捕获引用不会冻结所指对象。lambda 中 this 指外围实例，匿名类中 this 指匿名类实例。若行为复杂到局部难以阅读，应使用命名方法或命名类。

先认识这些词

函数式接口
只有一个抽象方法、为 lambda 提供目标类型的接口。
捕获
在 lambda 内使用外围作用域的值或引用。
事实上的 final
初始化后不再重新赋值的局部变量。

03 / 逐项读懂公式

Predicate<T>：T → boolean
Function<T,R>：T → R
示例：length -> length >= minimum
捕获的局部变量必须为 final 或事实上的 final

T 是输入引用类型，R 是结果类型。箭头描述函数形状的契约，不承诺实现纯净或没有副作用。minimum 是外围方法中的局部变量，捕获后不能重新赋值。代码块 lambda 若从语句返回值，需要明确 return。接口决定目标类型；lambda 不是脱离类型独立存在的通用函数。

04 / 先看一个完整例子

提醒系统使用 Predicate<Integer> overdue = days -> days >= 3。对 1、3、5 测试，依次得到 false、true、true。若阈值来自 int minimum = 3，只要此局部变量以后不重新赋值，lambda 就能捕获它。final List<String> log 也能捕获；log.add 仍能修改列表，因为 final 约束引用，不约束内容。若要有意改变规则，用新阈值构造新谓词。除非外围设计明确需要，不要把不断变化的领域状态隐藏在捕获的可变对象里。

    看答案

    不会。被捕获的局部引用不能重新赋值，但所指对象仍可变化。

  2. lambda 主体何时执行？

    看答案

    调用函数式方法时执行，不是仅在创建 lambda 时执行。

  3. lambda 内的 this 表示什么？

    看答案

    沿用外围实例上下文的含义；匿名类则引入自己的实例。

01 / 从一个故事开始

02 / 理解原理

先区分编译错误、运行时异常与错误结果。用最小但有用的输入复现，再在适当边界比较期望与实际。调试器可在断点暂停，查看局部变量和调用栈，单步进入或跨过方法，找出最早偏差。编译时保留调试信息可改善检查，具体命令取决于工具。修复原因，并在适当时保留聚焦回归测试。Javadoc 使用描述与 @param、@return、@throws 等标签记录公开契约。应说明假设、副作用、单位和异常行为。仅复述方法名字，不如精确说明调用者可以依赖什么。

03 / 逐项读懂公式

箭头表示调查循环。假设失败，就回到观察。接受输入包含范围、null 处理和单位。输出承诺在相关时包含顺序或状态保证。副作用说明修改及外部输入输出。失败行为说明异常，以及失败后仍成立什么。这些是概念类别，不是数学方程。文档与测试应遵循同一契约，让失败测试具有可解释含义。

包、访问控制与类图

01 / 从一个故事开始

一所学校有几栋楼。理科楼有实验室，艺术楼有工作室。每个房间都有完整的地址，即楼名加房间名，所以两栋楼都可以有“12 号房”而不会混淆。门遵循不同的规则。有的房间只给负责它的老师用。有的给这栋楼的教职工用。有的也给在其他楼工作的实习教师用。前厅则对所有访客开放。

校园地图不会画出每一张课桌。它画出各栋楼、主要房间，以及它们之间的连接。类图就是程序的这种地图。你可以在写任何代码之前手绘它，让你和团队在修改还很便宜的时候讨论设计。

02 / 理解原理

包把相关的类归在一个名字下。文件以 package 语句开头，例如 package shop.model;，它所在的文件夹必须与之对应：src/shop/model/Item.java。这个类的全名是 shop.model.Item。包可以防止命名冲突，把相关的类放在一起，还能控制访问。没有 package 语句的文件属于无名的默认包。做小测试没问题，但是它的类不能被导入。包名全部小写，库常常用倒写的域名开头。

import 语句让你可以写 Item 而不用写 shop.model.Item。import shop.model.*; 导入该包里的所有类，但不包括子包里的类。java.lang 里的类，如 String，不需要导入。import 不会加载任何东西，也不影响速度，只是缩短名字。如果两个包里有同名的类，就导入其中一个，另一个写全名。构建时运行 javac -d out src/shop/model/Item.java src/shop/app/Main.java，编译好的类会写入 out 下对应的文件夹。用 java -cp out shop.app.Main 运行程序。

访问修饰符控制谁可以使用一个类或成员。private 表示只有同一个类，另有一条额外规则：嵌套类和它的顶层类共享私有成员。不写修饰符，叫包级私有，表示同一个包。protected 表示同一个包，并且包括任何地方的子类。public 表示所有人。顶层类只能是 public 或包级私有。protected 成员还有一条规则：其他包里的子类，可以通过 this 或子类类型的引用使用它，但不能通过父类类型的引用使用它。设计上的原则是：给每个成员尽可能小的可见性。字段保持私有，辅助类保持包级私有，只把其他包必须使用的部分设为 public。

包也给应用提供结构。一家商店可以有 shop.model 放领域对象，shop.io 处理文件，shop.app 放 main。依赖应当单向：shop.app 使用 shop.model，而 shop.model 不导入 shop.app。包级私有的类对其他包隐藏了实现。

类图的方框分三部分：名称、属性和操作。符号表示可见性：+ 表示 public，- 表示 private，# 表示 protected，~ 表示包级。静态成员加下划线。抽象类或抽象方法用斜体，或标注 {abstract}。接口加标签 <<interface>>。方框之间的线有各自的含义。泛化（extends）是实线，三角形为空心，指向父类。实现（implements）是虚线，三角形为空心，指向接口。关联是普通的线，可以用箭头表示方向，用 1 或 0..* 之类的数字表示数量。聚合在“整体”一端画空心菱形。组合画实心菱形，表示部分离开整体就不能存在。依赖是虚线箭头，意思是“使用”。泛型类在名字里显示类型参数，例如 Catalog<T extends Shape>。

Javadoc 把以 /** 开头的注释变成 HTML 参考文档。第一句话是摘要。每个参数写 @param 名字，结果写 @return，异常写 @throws 类型和触发条件，相关条目写 @see，版本写 @since，应避免的东西写 @deprecated，句子里的代码写 {@code x}，链接写 {@link Class#method}。要写出调用者需要知道的内容：单位、是否允许 null、异常和副作用。用 javadoc -d docs -sourcepath src -subpackages shop 生成页面。

04 / 先看一个完整例子

假设文件 src/shop/model/Item.java 声明了 public class Item，其中有一行 protected int price;，而文件 src/shop/app/Gift.java 在包 shop.app 里声明了 class Gift extends Item。在 Gift 内部，price 和 this.price 都能编译。方法 Gift.cost(Item other) 如果读取 other.price，则无法编译，因为 other 的类型是 Item，不是 Gift。方法 Gift.cost(Gift other) 读取 other.price 则可以编译。shop.app 里不继承 Item 的类 Main，根本不能读 price。如果 price 不写修饰符，那么连 Gift 也不能使用它，因为 Gift 和 Item 在不同的包里。

再看文档。以一个把宽度分给 n 列的方法为例。注释可以先写摘要“Returns the width of one column.”。接着写 @param n，说明列数至少为 1。再写 @return，说明结果是以像素为单位的宽度。最后写 @throws IllegalArgumentException，说明 n 小于 1 时抛出。读生成页面的人不用打开源码，就知道单位和失败的情形。

再看图。这个设计有 5 个类和 1 个接口，有两条实线空心三角箭头（Rect 和 Triangle 指向 Shape），另一条（Square 指向 Rect），以及一条虚线箭头（Shape 指向 Describable）。

/** Not public, so it is package-private: only classes in this package can see the class itself. */
class Vault {
    private int secret = 7;
    int packageLevel = 1;
    protected int shared = 2;
    public int open = 3;

    int reveal() {
        return secret;
    }
}

/** A subclass. Inside one package it can use protected and package-level members. */
class Safe extends Vault {
    int total() {
        return shared + packageLevel + open;
    }

    // int bad() { return secret; }   // error: secret has private access in Vault
}

public class Main {
    /** Nested classes share their private members with the enclosing top-level class. */
    static class Counter {
        private int hidden = 5;
    }

    static final int CLASS = 1, PACKAGE = 2, SUBCLASS = 4, ANYONE = 8;

    /** Who may use a member declared with each modifier (JLS 6.6), as a set of places. */
    static int places(String modifier) {
        switch (modifier) {
            case "private":
                return CLASS;
            case "(none)":
                return CLASS | PACKAGE;
            case "protected":
                return CLASS | PACKAGE | SUBCLASS;
            default:
                return CLASS | PACKAGE | SUBCLASS | ANYONE;
        }
    }

    static String yesNo(int set, int place) {
        return (set & place) != 0 ? "yes" : "no";
    }

    public static void main(String[] args) {
        Vault vault = new Vault();
        Safe safe = new Safe();
        System.out.println("same package, package-private field: " + vault.packageLevel);
        System.out.println("same package, protected field: " + vault.shared);
        System.out.println("private field through a method: " + vault.reveal());
        // System.out.println(vault.secret);   // error: secret has private access in Vault
        System.out.println("subclass uses inherited members: " + safe.total());
        System.out.println("nested private seen by the outer class: " + new Counter().hidden);

        System.out.println();
        System.out.println("modifier   same class  same package  subclass elsewhere  anyone");
        String[] modifiers = {"private", "(none)", "protected", "public"};
        for (String modifier : modifiers) {
            int set = places(modifier);
            System.out.println(String.format("%-10s %-11s %-13s %-19s %s", modifier,
                    yesNo(set, CLASS), yesNo(set, PACKAGE), yesNo(set, SUBCLASS), yesNo(set, ANYONE)));
        }
    }
}

现在把同样的想法分到不同的包里。把 public class Vault 放在 src/shop/vault/Vault.java，属于包 shop.vault。把 Main 放在 src/shop/app/Main.java，属于包 shop.app，并写 import shop.vault.Vault;。这个类必须是 public，其他包才能导入它。这时 Main 可以使用 open；但不能使用 packageLevel，因为它是包级私有成员；也不能使用 shared，因为 Main 不是子类。在 shop.app 中写的 class Safe extends Vault 可以使用 shared 和 open，但仍然不能使用 packageLevel 或 secret。

import java.util.ArrayList;
import java.util.List;

/**
 * Something that can describe itself in one line.
 *
 * @since 1.0
 */
interface Describable {
    /**
     * Builds the description.
     *
     * @return a one-line description, never {@code null}
     */
    String describe();
}

/**
 * A flat shape with a whole-number area.
 *
 * <p>Subclasses supply {@link #area()}; the description is built here once.
 *
 * @see Rect
 * @see Triangle
 */
abstract class Shape implements Describable {
    private final String name;

    /**
     * Creates a shape.
     *
     * @param name the label used in descriptions, not {@code null}
     */
    protected Shape(String name) {
        this.name = name;
    }

    /**
     * Computes the area.
     *
     * @return the area in square units, never negative
     */
    public abstract int area();

    @Override
    public String describe() {
        return name + " area=" + area();
    }
}

/** A rectangle. */
class Rect extends Shape {
    private final int width;
    private final int height;

    /**
     * Creates a rectangle.
     *
     * @param width  the width in units, at least 1
     * @param height the height in units, at least 1
     * @throws IllegalArgumentException if either side is less than 1
     */
    Rect(int width, int height) {
        this("rect", width, height);
    }

    /**
     * Lets a subclass choose its own label.
     *
     * @param name   the label used in descriptions
     * @param width  the width in units, at least 1
     * @param height the height in units, at least 1
     */
    protected Rect(String name, int width, int height) {
        super(name);
        if (width < 1 || height < 1) {
            throw new IllegalArgumentException("sides must be at least 1");
        }
        this.width = width;
        this.height = height;
    }

    @Override
    public int area() {
        return width * height;
    }
}

/** A square is a rectangle whose sides match. */
class Square extends Rect {
    Square(int side) {
        super("square", side, side);
    }
}

/** A triangle given by its base and height. */
class Triangle extends Shape {
    private final int base;
    private final int height;

    Triangle(int base, int height) {
        super("triangle");
        this.base = base;
        this.height = height;
    }

    @Override
    public int area() {
        return base * height / 2;
    }
}

/**
 * A list of shapes of one kind.
 *
 * @param <T> the kind of shape stored; a Catalog&lt;Rect&gt; holds only rectangles
 */
class Catalog<T extends Shape> {
    private final List<T> items = new ArrayList<T>();

    /**
     * Adds an item.
     *
     * @param item the shape to store
     */
    void add(T item) {
        items.add(item);
    }

    /**
     * Finds the item with the largest area.
     *
     * @return the largest item, or {@code null} when the catalog is empty
     */
    T largest() {
        T best = null;
        for (T item : items) {
            if (best == null || item.area() > best.area()) {
                best = item;
            }
        }
        return best;
    }

    int size() {
        return items.size();
    }
}

    public static void main(String[] args) {
        Catalog<Shape> shapes = new Catalog<Shape>();
        shapes.add(new Rect(3, 4));
        shapes.add(new Triangle(6, 5));
        shapes.add(new Square(4));
        System.out.println("catalog holds " + shapes.size() + " shapes");

从对象模型到小型事件驱动应用

01 / 从一个故事开始

社区温室有传感器、控制策略和墙上显示屏。若显示屏自己决定全部浇水规则，修改画面可能意外影响植物照料。更好的职责分配是：模型存当前条件，策略更新状态，显示屏展示快照。按钮动作转换成模型请求。这也便于画图：方框表示职责，连线表示协作。图只有帮助解释行为时才有价值，单纯列出全部字段和方法，却不说明部件为什么组合，作用有限。

02 / 理解原理

小应用也需要明确职责。领域状态与规则留在模型对象中；输入解析和事件处理放在边界；显示层读取状态，不拥有无关领域决定。UML 类图可概括字段、操作、可见性与关系。泛化箭头表示继承，实现关系表示实现接口，关联表示协作。组合表示较强所有权，不是每个引用字段都算组合。包组织名称及可访问性。构建工具自动编译、解析依赖并执行可重复检查。事件驱动程序中，处理器把事件转成模型操作，显示过程读取结果。将逻辑更新与显示时机分开，可在不开图形窗口时测试相同行为。

先认识这些词

模型
表示应用领域数据与规则的部分。
事件边界
外部动作转换为经过验证的领域请求的位置。
依赖注入
把协作对象传入对象，而不是在内部固定创建它。

03 / 逐项读懂公式

事件 → 已验证命令 → 模型转移 → 显示状态
命令后状态 = update(先前状态, 命令)
设计检查：组件职责清楚；协作明确

事件是按钮点击等原始交互。已验证命令是输入经过检查的领域请求。update 表示模型转移逻辑，可以修改对象，也可返回新状态，只要契约明确。render 把状态转换为视图，不应偷偷推进无关领域规则。职责原则是设计启发，不是数值定律，也不要求每个类只能有一个方法。

04 / 先看一个完整例子

设计温室面板：Bed 模型存湿度，WateringPolicy 决定是否允许浇水，Dashboard 显示当前值。按钮事件为某个 Bed 请求 addWater(2)。处理器确定目标，模型验证数量并更新湿度，显示从新状态刷新。在以湿度单位计量的简化模型中，单元测试从 4 开始，加 2，检查 6，全程不开窗口。类图显示 Dashboard 关联 Bed 和策略接口，具体策略实现该接口。同样协作可先通过无界面命令接口练习，再添加图形视图。

一步步想清楚

  1. 为什么把规则放在按钮回调之外？

    看答案

    同一规则可在不开窗口时测试与复用。回调只负责把事件转换为请求。

  2. 谁决定是否允许浇水？

    看答案

    应由模型或明确策略强制执行规则。只禁用按钮无法约束其他调用者。

  3. 分离层次一定需要很多类吗？

    看答案

    不一定。先区分职责与方法契约；当所有权或可替换行为需要时再增加类。

  4. 为什么先计算结果，再压入历史？

    看答案

    操作可能拒绝输入。若先修改历史，撤销时可能取回完全相同的快照，看起来像没反应。应先校验，再提交状态变化。

public class Main {
    static final class Bed {
        private int moisture;
        Bed(int initial) {
            if (initial < 0 || initial > 10)
                throw new IllegalArgumentException("range");
            moisture = initial;
        }
        void water(int amount) {
            if (amount < 0 || amount > 10 - moisture)
                throw new IllegalArgumentException("range");
            moisture += amount;
        }
    }
    static String handle(Bed bed, String command) {
        String[] parts = command.split(" ");
        if (parts.length != 2 || !parts[0].equals("water"))
            return "unknown command";
        try {
            bed.water(Integer.parseInt(parts[1]));
            return "accepted";
        } catch (IllegalArgumentException ex) {
            return "rejected";
        }
    }
    static String render(Bed bed) {
        return "moisture=" + bed.moisture;
    }
    public static void main(String[] args) {
        Bed bed = new Bed(4);
        for (String command : new String[] {"water 2", "water 8", "water many"}) {
            System.out.println(command + " -> " + handle(bed, command));
            System.out.println(render(bed));
        }
    }
}

public class Main {
    static int apply(int current, java.util.function.IntUnaryOperator policy) {
        if (current < 0 || current > 10)
            throw new IllegalArgumentException("initial range");
        int amount = policy.applyAsInt(current);
        if (amount < 0 || amount > 10 - current)
            throw new IllegalArgumentException("amount range");
        return current + amount;
    }
    public static void main(String[] args) {
        java.util.function.IntUnaryOperator gentle =
            current -> Math.max(0, 6 - current);
        java.util.function.IntUnaryOperator dryDay =
            current -> Math.max(0, 8 - current);
        System.out.println("gentle=" + apply(4, gentle));
        System.out.println("dry day=" + apply(4, dryDay));
        try {
            apply(4, current -> 20);
        } catch (IllegalArgumentException ex) {
            System.out.println("unsafe policy rejected");
        }
    }
}

做一个可以撤销的小编辑器

米娜为校园展览编写标签。她追加一个词，发现不合适，想点击撤销。只保存最新文本就找不回上一步。她把文档、编辑动作分开，让编辑器用栈保存旧快照，同时规定被拒绝的动作不能进入历史。这样还没有制作按钮，就能测试编辑器。

import java.util.ArrayDeque;
import java.util.Deque;
public class Main {
    interface Edit { String apply(String text); }
    static final class Append implements Edit {
        private final String suffix;
        Append(String suffix) { this.suffix = suffix; }
        @Override public String apply(String text) {
            if (suffix == null || suffix.isEmpty())
                throw new IllegalArgumentException("empty edit");
            return text + suffix;
        }
    }
    static final class Editor {
        private String text = "";
        private final Deque<String> history = new ArrayDeque<>();
        void execute(Edit edit) {
            String next = edit.apply(text);
            if (next == null) throw new IllegalArgumentException("null result");
            history.push(text);
            text = next;
        }
        boolean undo() {
            if (history.isEmpty()) return false;
            text = history.pop();
            return true;
        }
        String text() { return text; }
    }
    public static void main(String[] args) {
        Editor editor = new Editor();
        assert !editor.undo();
        editor.execute(new Append("Hello"));
        editor.execute(new Append(" Python"));
        System.out.println(editor.text());
        try { editor.execute(new Append("")); }
        catch (IllegalArgumentException error) { System.out.println("rejected without history"); }
        if (!editor.undo()) throw new AssertionError("missing history");
        assert editor.text().equals("Hello");
        System.out.println("undo: " + editor.text());
    }
}

按执行顺序理解

  1. Edit 描述操作，Append 实现一种操作；Editor 无须知道新文本如何生成。

  2. 先计算并校验 next，再修改历史和正文。普通校验失败不会改变二者。

  3. push 记录旧文本，pop 取回最近快照，体现后进先出。

  4. 测试空历史撤销、两次成功操作、一次失败操作，再撤销。失败操作不能占用撤销步骤。

逐步读懂代码

状态转移是 text_next = edit(text_current)，历史保存之前的 text_current。String 不可变，因此保存引用就能保留旧快照，无须在每次入栈时复制字符。不过生成拼接后的新字符串仍需要与长度相关的时间和空间。大量长快照会占用较多内存。

分四步构建：定义有效文档，加入一种操作，加入历史，最后连接界面。按钮应调用 execute，而不是再维护另一份正文。这样测试不依赖屏幕事件。

这里约定 Edit 只计算文本，不产生外部副作用。撤销字符串无法撤回邮件或文件写入。这个小编辑器没有重做、持久化或并发编辑。文档很大时，可以先测量需求，再考虑保存逆操作或使用持久化文本结构。
